# 一个数字员工是如何被"编译"出来的

> 系列文章第二篇
> 2026-08-10，基于 UniEmployee 当前源码分析

上一篇我们介绍了 UniEmployee 的整体定位：数字员工是可配置、可执行、可审批、可观测的岗位资产。这一篇深入编译层，回答一个更具体的问题：当管理员在页面上配置好一个员工后，系统到底做了什么，才让一个"配置"变成一个会思考、会调用工具、会挂起等待审批的 Agent？

## 01 一切从一个岗位说明书开始

在 UniEmployee 中，一个数字员工的源头是一份结构化的 `EmployeeSpec`。它包含：

- `id` / `name` / `role`：员工的身份与岗位；
- `model`：使用的模型，支持 OpenAI 兼容协议；
- `persona`：人设与工作原则；
- `skills` / `tools` / `kbs` / `sops` / `connectors`：挂载的能力资源；
- `interrupt_on`：哪些工具需要人工审批；
- `backend`：使用普通状态后端还是本地执行后端；
- `subagents` / `subagent_policy`：可委派的子代理与委派策略。

内置员工以 YAML 形式存在，例如"小苏"的配置里会写明"产品咨询必须先查知识库""投诉必须先读投诉处理规程""退款必须走审批流程"。这些不是给人看的文档，而是编译器的输入。

## 02 配置先落库，运行时以 catalog.db 为准

YAML 只是种子源。首次启动时，`seed_if_empty()` 会把员工、技能、工具、知识库、SOP、连接器写进 `catalog.db`，之后管理员在资源中心做的所有配置都以数据库为准。

运行时读取链路是：

```text
catalog.db 关联表（employee_skills / employee_tools / employee_kbs / employee_sops / employee_connectors）
  -> get_employee_config() 拼出员工完整配置
  -> build_spec() 转成 EmployeeSpec
  -> compile_agent() 编译为可运行 Agent
```

普通用户还有一层个性化：`get_effective_config()` 按照"模板基础 + add - remove"合并该用户对员工能力覆盖。因此同一个员工，在不同用户面前可能拥有不同的有效技能或工具集合。

## 03 编译四件事

`compile_agent()` 是真正的深度模块。它接收 `EmployeeSpec`，做四件事后返回可运行的 Agent。

### 第一件事：把规程播种进 Store

技能不会全部塞进 system_prompt。编译器会遍历员工选中的技能，读取 SKILL.md 全文，写入 Store 的 `/skills/` 命名空间；SOP 全文写入 `/sops/`。同时从 SKILL.md 中提取触发条件，生成精简的"技能路由"摘要。

这保证了两点：

1. 模型在每轮对话中只看到"什么情况该调什么技能"；
2. 需要执行时，通过 `read_file` 读取完整规程，而不是靠记忆。

### 第二件事：装配工具

工具装配不是简单的列表拼接，而是按来源分类：

| 来源 | 说明 |
| --- | --- |
| 本地工具注册表 | `create_ticket`、联网搜索、时间、产品知识等原子工具 |
| 闭包工具 | `kb_search` 按员工的知识库配置动态生成，运行时实时读库 |
| 工厂工具 | `start_refund` 需要注入运行时 checkpointer，用于内层状态机的挂起恢复 |
| 通用工具 | `get_current_time` 无条件注入所有员工 |
| 本体工具 | `ontology_find_entities` / `ontology_query_relations` 按用户租户生成 |
| MCP 连接器 | 通过 `MultiServerMCPClient` 拉起 CRM、新闻等外部工具 |

特别要说明的是闭包工具。它们捕获了"当前员工是谁、当前用户是谁"的上下文，运行时查询的是最新配置，而不是编译期固化下来的快照。知识库条目增删改后，不需要重新编译员工。

### 第三件事：组装 system_prompt

最终提示词按固定顺序拼接：

```text
人设 persona
+ 技能路由（触发条件 + 规程路径）
+ SOP 路由（清单 + 摘要）
+ 业务本体路由（先查实体，再查关系）
+ 子代理委派说明
+ 子代理策略
```

每一段都是"规则"而不是"资料"。完整资料留在 Store 和知识库里，规则负责告诉模型该去哪里拿、什么时候执行。

### 第四件事：选择执行后端并创建 Agent

普通员工使用 `StateBackend`，数据分析、销售等需要执行脚本的员工使用 `LocalShellBackend`。两者之上再包一层 `CompositeBackend`，提供四条虚拟路径：

- `/data/`：按用户隔离的工作区，用于脚本、报表、看板；
- `/memories/`：用户级长期记忆；
- `/skills/`：技能全文；
- `/sops/`：SOP 全文。

最后调用 `create_deep_agent()`，把模型、工具、技能、记忆、checkpointer、store 和审批策略组装成 LangGraph Agent，并返回用于前端展示的阶段元信息。

## 04 缓存、失效与热更新

编译是有成本的：模型初始化、MCP 子进程拉起、技能播种都需要时间。因此 `runtime.get_agent()` 会缓存已编译 Agent：

- 管理员视角缓存键是 `employee_id`；
- 普通用户视角是 `employee_id|user_id`，用户级覆盖互不干扰；
- 服务启动时 `warmup_all()` 会预热所有员工，用户首次对话不用等待编译。

配置变更走"失效重编译"：管理员修改员工配置后调用 `runtime.invalidate()`，下次请求按新配置重建。技能和 SOP 内容变更是例外，它们只刷新 Store，不重建 Agent，这是"运行时资源"与"编译期配置"分层的结果。

## 05 两个容易踩的坑

### 坑一：记忆命名空间必须在编译期确定

长期记忆的 namespace 是 `(user_id, employee_id)`。它必须在编译期由闭包捕获，不能等运行时从配置里取。原因很具体：Agent 加载记忆的阶段早于运行时配置就绪，运行时再取会取不到，导致"能写进去、读不出来"。

所以 `get_agent()` 在编译前就知道当前用户，并把 `user_id` 闭包进 `memory_namespace()`，同一个员工的用户级变体天然隔离。

### 坑二：MCP 失败不能拖垮编译

MCP 连接器初始化失败时，编译层会捕获异常、打印日志、降级为"只有本地工具"，服务继续启动。这保证了外部连接器暂时不可用不影响其他能力。项目也提供了 `MCP_DISABLED=1` 的运维开关，用于紧急隔离问题。

## 06 新增一个员工意味着什么

站在产品视角，新增员工通常只需要四步：

1. 编写一份员工 YAML，定义人设、技能、工具、连接器和审批策略；
2. 在种子注册表登记该员工默认选择的能力；
3. 如果用到新工具，在工具注册表登记；
4. 重启服务，让种子写入 catalog.db 并预热。

编译层本身零改动。这正是 UniEmployee 把"数字员工"产品化的关键：**岗位的差异化通过配置表达，平台的差异化通过编译层沉淀。**
