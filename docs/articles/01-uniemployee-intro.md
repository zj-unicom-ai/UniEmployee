# 让 AI 成为员工，而不是聊天机器人：UniEmployee 数字员工平台解读

> 系列文章第一篇
> 2026-08-10，基于 UniEmployee 当前仓库源码、文档与实现分析

## 01 一个企业里反复出现的场景

一家公司决定引入 AI：客服想让它解答产品咨询，销售想让它写方案文档，经营团队想让它分析利润下滑原因，HR 想让它回答人事制度问题。

第一天大家很兴奋。一个月后发现：

- 客服机器人回答参数时会编，遇到投诉只会道歉，不会登记工单；
- 销售助手能写出一段"看起来很专业"的方案，但客户档案、产品资料、竞品信息全靠模型猜；
- 数据分析工具可以跑代码，但没人能确认它用的是哪张表、哪个口径，也不敢让它在真实订单上执行；
- 所有高风险动作都需要人工兜底，可系统里根本没有审批机制；
- 出了问题，没人知道 AI 当时调了哪些工具、看了哪些资料、为什么给出这个结论。

这不是"模型不够聪明"的问题。这是把 AI 当成"聊天机器人"在使用，而不是当成"员工"在管理。

UniEmployee 想回答的问题只有一个：**能不能把优秀员工的工作方式，沉淀成一个企业可以配置、执行、审批、观测和持续运营的数字劳动力平台？**

## 02 UniEmployee 是什么

UniEmployee 是一套面向企业的数字员工构建与运行平台。它不追求做一个通用的对话入口，而是把数字员工建模为一种可管理的岗位资产，让大模型按照企业设定的岗位职责、技能规程、业务流程、知识边界和审批规则去工作。

它的技术底座是 FastAPI + LangGraph/deepagents + Vue 3，模型侧兼容任意 OpenAI Chat Completions 协议的服务，数据默认落在本地 SQLite，既可以单机快速启动，也可以通过 Docker 部署。

平台的顶层抽象是一个五层能力模型：

```text
Employee（数字员工：人设 / 模型 / 技能 / 工具 / 知识库 / SOP / 连接器）
  |
  |-- Workflow / SOP（状态机工作流 + 业务规程）
  |-- Skill（SKILL.md 技能规程，触发条件 + 完整步骤）
  |-- Connector（MCP 连接器：CRM / 新闻 / RAGFlow 等外部系统）
  +-- Tool（原子工具：工单 / 搜索 / 知识库 / 本体查询 / 时间等）
```

用一句话概括：**员工是配置，能力是规程，动作是工具，风险是审批，运行是可观测。**

## 03 项目的核心特点

### 特点一：员工是一种可配置、可复用的资产

在 UniEmployee 里，"新建一个数字员工"不是写代码，而是配置一份岗位说明书：

- 人设与岗位边界；
- 使用的模型；
- 挂载的技能、工具、知识库、SOP、MCP 连接器；
- 需要人工审批的动作；
- 可委派的子代理。

这些配置写入 `catalog.db`，运行时以数据库为准。管理员在资源中心勾选能力后，系统会失效缓存并按新配置重新编译员工，不需要重启服务。用户还可以获得员工分配和个性化覆盖，让同一岗位在不同用户面前拥有不同的有效能力。

当前内置了 5 个岗位样例：售前售后客服小苏、数据分析专家小数、客户经理小小、综合人力专员 HR 小智、经营分析与决策顾问小经。新增员工只需要新增 YAML 模板并注册种子，编译层几乎零改动。

### 特点二：经验不是写进 Prompt，而是沉淀为规程

通用聊天机器人把"知识"全部塞进提示词，结果就是 prompt 越长、越贵、越不可控。UniEmployee 的做法是双通道：

- **路由摘要进 system_prompt**：从 `SKILL.md` 中提取触发条件和规程路径，让模型知道"什么情况该调什么技能"；
- **完整规程进 Store**：SKILL.md 全文按需读取，模型命中技能后必须先 `read_file` 查阅完整步骤，不允许凭记忆跳过。

SOP 也采用同样的思路：只把清单和摘要放进提示词，全文放在 Store 的 `/sops/` 虚拟路径下运行时读取。技能和 SOP 内容变更后只需刷新 Store，不需要重新编译员工，避免"改一行文档就重建整个 Agent"。

更硬核的流程还会固化成 LangGraph StateGraph 状态机。以退款为例，流程被建模为 `校验订单 -> 计算金额 -> 人工审批 -> 生成退款单` 四个显式节点，审批不是外部拦截，而是状态机内的一个挂起节点。这样每一步的状态、输入输出、审批点都确定可见。

### 特点三：知识从"能搜到"走向"能引用、能行动"

平台的知识层经历了从 FAQ 关键词检索、产品 Wiki 到 RAGFlow 向量检索的演进。当前 `kb_search` 直接调用 RAGFlow，返回结果带来源与相似度，员工回答时标注依据，从机制上抑制编造。

在此基础上，项目正在推进企业业务本体（Ontology）：把组织、部门、岗位、员工、客户、产品、项目、合同、订单定义为实体类型，用"负责、跟进、下单、包含"等关系把它们连成一张可查询的业务网络。数字员工回答"李晓芳负责哪些项目""华芯半导体下过哪些订单"这类问题时，先查本体再作答，而不是让模型猜。

当前代码中已经包含本体 schema、演示企业数据和可视化维护界面，团队还在持续建设语义关联、知识分桶和检索调试面板。这是本文系列后面要展开的重点之一。

### 特点四：数字员工有"手"，而且每一只手都被管理

平台通过几类工具让 AI 真正干活：

- **MCP 连接器**：按 MCP 标准接入外部系统，支持 Python stdio（如 CRM）和 npx 类型（如新闻检索）；
- **本地原子工具**：工单登记、联网搜索、当前时间、知识库检索、本体查询等；
- **工厂工具**：退款工具在编译期注入运行时 checkpointer，才能支撑内层状态机的暂停与恢复；
- **子代理委派**：经营分析员工可以把市场调研、产品检索等工作委派给专用子代理，避免主对话被长任务拖住；
- **代码执行**：数据分析类员工可以在按用户隔离的工作目录中运行受限 Python 代码，生成报表和看板。

工具不是"模型想调就能调"，而是按员工配置装配，普通工具统一注入，审批工具需要人工放行。

### 特点五：人机协同是设计出来的，不是事后补救

UniEmployee 实现了双路径审批：

- **轻量审批**：工单登记等动作通过外层 Agent 的 `interrupt_on` 拦截，等待批准或拒绝；
- **内化审批**：退款等业务流程在 StateGraph 内部挂起，审批单记录内层线程 ID，审批人做出决策后先恢复内层状态机，再恢复外层对话。

审批单持久化到独立的 SQLite 库，支持过期自动拒绝和 pending 数量上限。也就是说，AI 可以做完整流程，但关键动作必须由人把关，且整个链路可追踪。

### 特点六：AI 有记忆，而且记忆是隔离的

每个用户与每个员工之间有一份独立的长效记忆，按 `(user_id, employee_id)` 命名空间隔离并落盘。客服能记住客户偏好，分析师能记住用户的分析习惯，销售能记住客户需求。不同用户问同一个员工，互不串记忆。

### 特点七：一切运行都可观测、可回放

每次对话或审批恢复都记为一次 run，记录模型调用、工具调用、输入输出、耗时和 token 消耗。前端通过 SSE 实时推送思考、工具调用、技能激活、子代理、审批等阶段事件，管理员可以回放"AI 到底做了什么"。

错误处理也做了分级：超时、限流、上下文超长、鉴权失败分别映射为稳定的错误码，避免把内部异常直接暴露给前端。

### 特点八：平台治理与交付形态贴合企业现实

- 鉴权：bcrypt + JWT，管理员与普通用户权限分离；
- 安全基线：强制改密、登录限流、前端 XSS 消毒、接口鉴权拦截；
- 数据资产：7 个 SQLite 库覆盖目录、会话、checkpoint、记忆、Trace、审批和本体，统一备份脚本；
- 部署：单进程即可全功能，也可 Docker Compose 一键启动；
- 渠道：已提供 Web 聊天和 IM 频道的扩展架构，非 Web 渠道可通过 Webhook 接收消息、回推回复，企业微信、飞书、钉钉等渠道正在规划中。

## 04 它到底解决了什么问题

| 企业痛点 | 传统做法的问题 | UniEmployee 的做法 |
| --- | --- | --- |
| AI 回答不可靠、爱编造 | 通用聊天机器人 + 长 Prompt | 技能路由 + 知识库/本体先查 + 来源标注 |
| 每个部门各自造机器人 | 重复建设、口径不一、难以管理 | 员工=配置，资源中心统一沉淀和复用 |
| AI 只回答、不干活 | 对话结束，流程断裂 | MCP/工具接入业务系统，StateGraph 固化多步流程 |
| 高风险动作不敢放权 | 要么全自动，要么全人工 | HITL 审批节点 + 持久化审批单 + 可恢复执行 |
| 老员工经验留不住 | 人走了，知识就没了 | SKILL/SOP/知识库/记忆持续沉淀 |
| 出问题查不清 | 黑箱输出，无法追责 | 全链路 Trace + token/耗时统计 + 错误分级 |
| 渠道碎片化 | 每个 IM 分别对接 | 统一频道抽象，Web 已实现，外部 Webhook 已预留 |
| 系统接入成本高 | 每个工具单独开发 | MCP 标准 + 工具注册表 + 连接器配置化 |

## 05 对企业的价值

**第一，把 AI 投入从"试试看"变成"可上岗"。** 一个数字员工不是聊天界面，而是一个岗位的完整工作方式：小苏处理咨询时会查知识库、查订单、按投诉规程安抚、登记工单、发起退款审批；小小会查客户档案、检索产品方案、委派调研、生成方案文档；小经会先跑真实数据、再做归因、再给决策建议。这些是完整的工作闭环，不是单点问答。

**第二，降低 AI 应用的交付成本。** 新增一个岗位通常不需要新写一套系统，而是复用技能、工具、知识库、连接器等资源并重新装配。企业积累的是可复用的能力目录，而不是一个又一个无法协同的机器人。

**第三，让 AI 可用在真实业务上。** 审批、权限、Trace、来源标注共同构成"敢让 AI 做正事"的治理基础。流程固化保证多步任务不丢步，审批保证高风险动作有人负责，Trace 保证任何结论都能被审计。

**第四，知识资产化。** 员工手册、产品资料、经营口径、投诉规程、成功案例都会被组织成数字员工可查询、可引用、可执行的资产。知识库从"存档"变成"生产工具"。

**第五，自主可控。** 数据默认本地存储，模型走 OpenAI 兼容协议，可以在私有化环境部署，按企业需要接入自己的模型服务。

## 06 当前边界与路线图

为了让读者不被"PPT 价值"误导，这里如实说明现状：

- 内置 CRM 和订单数据目前是演示 mock，生产环境需要替换为真实业务系统；
- 知识库依赖 RAGFlow 实例，未配置时会明确提示，而不是伪装成可用；
- MCP 动态加载、多租户隔离、员工配置版本化、技能版本回滚等仍在路线图中；
- 微信、企业微信、飞书、钉钉等 IM 渠道目前是架构预留，正式接入尚未发布；
- 多实例部署、共享缓存、配额治理属于生产化课题，项目已在 TODO 中规划。

这些边界恰恰说明平台是在往"可运行的企业平台"走，而不是一个演示壳。
