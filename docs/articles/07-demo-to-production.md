# 从 Demo 到生产：落地时最该先解决什么

> 系列文章第七篇（收尾篇）
> 2026-08-10，基于 UniEmployee 当前源码与路线图分析

前六篇讲了 UniEmployee 的定位、编译机制、技能与知识、业务本体、人机协同和可观测性。最后这篇不写理想状态，写现实：一个演示项目要变成企业生产系统，最先要解决什么。

## 01 先承认现状

在规划生产化之前，必须把当前版本的边界说清楚：

- 内置 CRM、订单、客户数据是演示 mock，不是真实业务数据；
- 运行架构是单进程 + SQLite + 内存缓存，天然适合中小规模验证；
- Agent 缓存目前是进程内字典，没有淘汰上限；
- MCP 连接器在编译期拉起，生命周期治理仍在路线图中；
- 数据分析类的本地执行能力强大，生产环境必须做更严的环境隔离；
- 多租户字段已经预留，但完整的多租户隔离尚未全部落地。

这些不是缺点，而是"先跑通业务，再补生产短板"的取舍。接下来按影响排序，给出落地检查清单。

## 02 第一步：选一个能被验证的场景

不要一开始就做全公司数字员工。选择一个场景，它最好同时满足：

- 频率高：每天都有大量重复咨询或操作；
- 边界清晰：职责、知识、工具都能说清楚；
- 结果可验证：AI 答得对不对、办得成不成，有明确判断标准；
- 风险可控：即使出错也不会造成重大损失。

客服咨询、经营数据查询、HR 制度问答都是好的起步场景。退款、审批、对外发文档这类场景适合第二步再加。

## 03 第二步：数据与系统接入

演示数据必须换成真实数据源。这一步建议按"只读优先"推进：

1. 先接只读查询：CRM 客户档案、订单状态、产品资料、经营数据；
2. 再接写操作：工单创建、文档生成、审批执行；
3. 高风险写操作必须过审批；
4. 建立数据归属：每个员工能查哪些数据、哪些用户能看哪些结果，由配置和权限共同决定。

连接器层已经有 MCP 标准，生产环境把它接到真实系统即可。关键不是"能不能连"，而是"连上之后权限是否仍然有效"。

## 04 第三步：知识资产化

数字员工的能力上限取决于知识质量。落地时要建立知识治理：

- **来源管理**：每个知识库文档有负责人、版本和更新时间；
- **口径管理**：指标口径、制度条款要统一，过时内容要标记；
- **来源标注**：让 AI 回答时带依据，方便核验；
- **本体优先**：客户、组织、订单这类实体关系用本体管理，不要塞进文档；
- **评测闭环**：准备一组黄金用例，每次知识变更后跑一遍，防止 AI 引用旧口径。

知识建设没有"一步到位"，但要有一个可持续的更新流程。

## 05 第四步：安全与治理

生产环境的安全基线包括：

- `JWT_SECRET` 必须改为随机长串，并支持轮换；
- 所有接口保持鉴权，审批接口校验审批单归属；
- 本地执行环境必须收紧：限制工作目录、限制环境变量、加资源配额；
- 登录限流要支持多实例，不能只依赖单进程内存；
- 前端 token 建议迁移到 HttpOnly Cookie，并配套 CSRF 防护；
- 所有 AI 的高风险动作默认进审批，审批记录保留审计。

安全不是上线前补，而是从接入真实数据那一刻就开始。

## 06 第五步：运行时生产化

当用户量和场景数量上来后，需要逐项升级运行时：

| 能力 | Demo 状态 | 生产目标 |
| --- | --- | --- |
| 模型配置 | 单模型字符串 | 主模型 + 回退 + 超时 + 重试 |
| Agent 缓存 | 进程内字典 | LRU + 上限 + 淘汰时关闭 MCP |
| MCP 生命周期 | 编译期拉起 | 注册中心 + 热更新 + 健康检查 + 重连 |
| checkpointer | SQLite | Postgres / Redis，支持多实例 |
| 多租户 | 字段预留 | 查询层统一租户过滤 |
| 配额 | 无 | 按租户 / 用户 / 员工限流与 token 配额 |
| 版本管理 | 无 | 员工配置与技能版本化，可回滚 |
| 运维中心 | Trace 回放 | 错误分布、资源指标、告警 |

这些在 TODO 中都有对应专项，属于"需要投入但方向明确"的部分。

## 07 第六步：运营闭环

上线不是终点。建议建立三类运营动作：

**日报**：每天看各员工对话量、成功率、token 成本、审批通过率；

**周评**：抽检错误 Trace，把"没读技能""知识库没命中""工具参数错"归类，推动内容或配置改进；

**版本迭代**：配置变更像发版一样记录，技能和知识库更新要有责任人，重要变更先小范围灰度。

渠道方面，生产环境通常需要把员工接到企业微信、飞书或钉钉。当前平台已经预留 IM 频道和 Webhook 架构，落地时优先接入员工最常用的一个渠道，而不是同时接全部。

## 08 推荐的落地顺序

把上面的内容压缩成一个可执行路径：

1. 选场景：高频、清晰、可验证；
2. 建知识：把该岗位需要的资料整理进知识库，定义好口径和来源；
3. 配员工：用现有技能、工具、连接器组装出第一个生产员工；
4. 接数据：先只读接入真实系统，跑通后加写操作；
5. 开审批：给高风险工具配置审批，让 Trace 记录每一次决策；
6. 定评测：建立黄金用例，把"AI 答得好不好"变成可量化的指标；
7. 收渠道：接入一个真实 IM 渠道，让业务人员日常使用；
8. 再扩展：把验证过的技能和知识复用到下一个岗位。

## 09 写在最后

UniEmployee 的核心命题是：AI 要成为企业员工，而不只是聊天窗口。员工需要岗位说明书、需要培训资料、需要工具权限、需要领导审批、需要绩效考核。这个平台做的，就是把数字员工的这套管理体系搭出来。

当前版本已经跑通了从配置、编译、执行、审批到 Trace 的完整闭环。剩下的工作不是"要不要做"，而是"先做哪一个岗位、接哪一套数据、用什么指标证明它比人工更好"。这个选择，最终要由业务一起决定。
