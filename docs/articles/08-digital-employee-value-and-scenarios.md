# UniEmployee：让大模型从“聊天助手”进化为“可上岗的数字员工”

> 把专业员工的经验、流程和判断标准，固化成随时上岗、可配置、可审批、可观测的 AI 数字员工——这不是又一个 ChatGPT 套壳，而是一套面向企业的数字员工构建与运行平台。

## 一、为什么需要“数字员工”？

过去两年，几乎所有企业都试过把大模型引入业务，但大多数停留在两种形态：

- **个人效率工具**：员工各自开个聊天窗口，问答完就关，经验不沉淀，能力不共享；
- **嵌入式客服机器人**：接了个 FAQ 问答接口，答非所问时只能人工兜底，没人敢让它独立干活。

根本问题在于：**大模型有“智力”，但没有“岗位”**。它不知道企业的业务规则，不记得昨天和客户聊了什么，高风险操作没人把关，出了问题无从追溯。

UniEmployee（数字员工平台）的答案是：像对待一名新员工那样，给 AI 一个完整的“入职流程”——人设、技能、工具、知识库、SOP、审批权限，全部页面化配置，让它真正**承担一个岗位的工作**，而不只是回答问题。

## 二、五大核心特点

### 1. 五层能力模型：把 AI 编排成“组织生产力”

UniEmployee 用一个清晰的能力栈来定义数字员工：

```
Employee ── 数字员工（人设 / 模型 / 技能 / 工具 / 知识库 / 连接器装配）
   ├── Workflow / SOP ── 状态机工作流与技能规程
   ├── Skill ── 技能（SKILL.md 规程，按需查阅）
   ├── Connector ── MCP 连接器（CRM / 新闻 / RAGFlow）
   └── Tool ── 原子工具（工单 / 搜索 / 文档生成 / 数据分析）
```

平台内置 5 个开箱即用的数字员工：**小苏**（客服）、**小数**（数据分析师）、**小晓**（销售顾问）、**HRBP**（人力资源伙伴）、**小经**（经营分析顾问，还带市场调研子代理）。它们不是 demo 玩具——每个员工都有完整的人设、知识库、工具链和业务流程。

### 2. 流程型技能与 SOP：关键流程不靠“记忆”，靠“状态机”

这是 UniEmployee 最工程化的设计之一。很多 Agent 平台的“技能”就是把提示词拼进 system prompt——模型心情好就执行，上下文一长就跳步。

UniEmployee 的做法不同：

- **技能以 `SKILL.md` 规程沉淀**，包含触发条件与执行步骤，播种进知识存储，模型运行时按需查阅，而不是凭记忆发挥；
- **关键业务流程用 StateGraph 状态机固化**。以退款流程为例：`校验订单 → 计算退款 → 人工审批 → 执行退款`，每一步状态落库，中途断电重启也能从断点恢复。

流程就是流程，不多一步、不少一步。

### 3. 企业知识本体：回答要“有据可查”

数字员工答错业务问题的代价很高，所以 UniEmployee 在知识管理上做了三件事：

- **多源知识接入**：产品 FAQ、Markdown 产品 Wiki、RAGFlow 向量检索深度知识库，回答自动标注来源；
- **知识本体化演进**：知识正从“文档检索”升级为带业务语义的结构化资产——按源文档、主题、操作手册、业务规则等概念类型组织，规则关联流程、流程关联文档，检索到的是关系网络而非孤立片段；
- **知识分桶**：不同岗位员工调用不同知识范围，避免跨域串扰——客服不会拿销售话术回答投诉。

### 4. HITL 人工审批：高风险动作，人来把关

数字员工要真正干活，就必须能执行动作：创建工单、发起退款、生成方案文档。但企业不会放心让 AI 全自动操作。

UniEmployee 内置**人机协同审批闭环**：高风险动作触发流程中途中断，生成审批单（SQLite 落库、带过期自动拒绝），人工批准后流程自动继续。审批等待期间服务重启也不丢单——这对企业落地是刚需。

### 5. 全链路可观测 + 长期记忆：可审计、可进化的 AI 同事

- **每次对话 = 一条完整执行记录**：LLM 调用、工具输入输出、耗时、token 消耗全部落库，支持回放定位——“AI 为什么这么回答”从此有答案；
- **跨会话长期记忆**：按 `(用户, 员工)` 双维度隔离落盘，重启不丢。数字员工记得住客户的偏好和历史，越用越懂你的业务；
- **超长对话自动压缩**：基于窗口比例智能触发，旧消息折叠为摘要、完整历史落盘可回读，长对话不爆上下文、不中断——这是客服、顾问类岗位天天遇到的场景。

## 三、价值：给谁解决什么问题？

**对企业决策者：**

- **专家经验资产化**：资深客服的处理套路、销售的方案逻辑，沉淀为平台的技能与 SOP，不随人员流动而流失；
- **可控可审计**：JWT 鉴权、登录限流、强制改密、XSS 消毒、审批留痕，安全基线开箱即用；
- **低成本起步**：纯本地 SQLite 落盘、单进程全功能、Docker 一键部署，任意 OpenAI 兼容模型接口（DeepSeek、GLM、Qwen 均可）即可运行，不需要 GPU。

**对技术团队：**

- **MCP 标准生态**：通过 Model Context Protocol 接入 CRM、新闻等外部系统，stdio 与 npx 两种形态，业务系统扩展只需写一个 MCP server；
- **页面化配置**：员工、技能、工具、知识库、连接器全部在管理后台 CRUD，运行时以目录库为准，改配置不用改代码；
- **31 个测试文件**护航，软删除、数据隔离、技能注入、流式错误分级这些坑都提前踩过。

**对业务用户：**

像使用一名真正的同事那样使用数字员工：在 Web 聊天中选择岗位对应的员工，直接派活，遇到审批卡片点一下，剩下交给流程。

## 四、典型应用场景

| 场景 | 数字员工 | 工作方式 |
|------|---------|---------|
| **智能客服** | 小苏 | FAQ + 投诉处理技能 + CRM 连接器，查客户、查订单、答政策，复杂投诉按 SOP 逐级处理，必要时创建工单触发审批 |
| **经营数据分析** | 小数 | 安全沙箱内运行 Python 分析销售数据集，产出结论而非数字，全程可回放 |
| **销售支持** | 小晓 | 结合产品 Wiki 与 CRM 客户画像，按企业销售技能生成定制化方案文档 |
| **HR 服务** | HRBP | 回答政策类问题有知识库溯源，敏感操作走人工审批 |
| **经营决策分析** | 小经 | 经营全景 → 归因分析 → 决策建议，还能派出市场调研子代理收集情报 |

一个真实的使用闭环：客服小苏接到退款诉求 → 自动校验订单（CRM 连接器）→ 退款流程状态机启动 → 金额超阈值触发人工审批 → 管理员在审批中心批准 → 退款执行 → 全程 Trace 可回放。**这就是“数字员工”与“聊天机器人”的区别。**

## 五、技术架构一览

- **后端**：Python 3.12 + FastAPI + deepagents + LangGraph StateGraph，SSE 流式响应
- **前端**：Vue 3 + Vite + Naive UI + Pinia 管理后台，单进程内嵌静态文件
- **存储**：6 个 SQLite 库各司其职（目录 / 会话 / 检查点 / 记忆 / 追踪 / 审批），`APP_DATA_DIR` 可重定向，容器挂载即持久化
- **部署**：`git clone` → 填 `.env` → `uvicorn` 一条命令启动，或 `docker compose up` 一键容器化

```bash
git clone https://github.com/zj-unicom-ai/UniEmployee.git
cd UniEmployee && cp .env.example .env   # 填入模型 API Key
python3 -m venv .venv
.venv/bin/pip install -r backend/requirements.lock.txt
PYTHONPATH=backend .venv/bin/uvicorn app.main:app --port 8787
```

打开 `http://localhost:8787`，默认管理员登录后，5 个数字员工已经“到岗”。

## 六、路线图：我们在往哪走

UniEmployee 正在向更深的 enterprise 能力演进：

- **多渠道 IM 接入**：微信 / 企业微信 / 飞书 / 钉钉，频道扩展架构已就绪；
- **知识本体深化**：概念类型化、语义关联、检索调试面板，让知识治理可视化；
- **多副本部署**：Redis 化的限流、会话与缓存，支撑企业级规模；
- **多员工协作**：一个会话内多个数字员工分工协作，模拟真实团队作业。

## 写在最后

AI 落地企业的下一站，不是更强的模型，而是**更完整的岗位化工程**——让 AI 拥有岗位的知识、流程的约束、动作的权限和行为的可追溯性。

UniEmployee 把这套工程开源出来，希望更多团队可以低成本地构建属于自己的数字员工队伍。
