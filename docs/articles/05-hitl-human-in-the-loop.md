# 人机协同：AI 干活，人把关

> 系列文章第五篇
> 2026-08-10，基于 UniEmployee 当前源码分析

企业引入 AI 后遇到的第一个现实问题是：AI 能干活，但企业敢不敢让它干完？退款要动钱，工单要派给售后，方案文档要发给客户。如果 AI 自动执行一切，出了错谁来负责？如果每一步都等人，AI 又失去了自动化的意义。

UniEmployee 的答案是"关键动作停下来，人工批准后继续"。这不是把 AI 关进笼子，而是把审批设计成执行流程的一个节点。

## 01 两种需要审批的场景

平台里存在两类审批需求：

1. **轻量审批**：调用某个工具本身需要确认，例如登记工单；
2. **流程内审批**：多步流程中间需要人工决策，例如退款必须经过"校验订单 -> 计算金额 -> 审批 -> 执行"。

两者在实现上完全不同：轻量审批靠外层 Agent 拦截工具调用，流程内审批靠内层状态机的挂起节点。UniEmployee 把两条路径都实现了，并且通过审批单统一管理。

## 02 轻量审批：外层拦截

工具在 catalog.db 中有一个 `needs_approval` 标记。员工配置时会根据所选工具自动推导 `interrupt_on`：

```text
工具配置了 allowed_decisions: [approve, reject]
  -> 编译时该工具的调用会触发 Agent 中断
  -> SSE 向前端推送 approval_required 事件
  -> 审批人决策后，以 Command(resume=...) 恢复外层 Agent
```

模型调用这类工具时会停下，不能自己"假装批准"。审批人拒绝后，模型会收到拒绝消息并按此调整回答。

## 03 流程内审批：内层状态机

退款是平台最有代表性的流程内审批。它没有简单拦截一个工具调用，而是把审批放进了 LangGraph StateGraph：

```text
validate_order（校验订单存在、已签收、7 天内）
  -> calc_refund（计算退款金额）
  -> await_approval（interrupt 挂起，等待人工决策）
  -> execute_refund（批准生成退款单，拒绝生成拒绝说明）
```

这里有几个关键设计：

**审批是显式节点。** `await_approval` 用 `interrupt()` 原语挂起状态机，流程明确知道自己"卡在审批"，不是被外部机制临时打断。

**内层线程与外层隔离。** 每次退款运行在一个派生的线程 ID `refund:{order_id}:{reason_hash}` 上，不污染外层对话线程，也保证重启后还能定位到同一次审批。

**审批通过后链路不断。** 审批人做出决策后，系统先恢复内层状态机执行退款，拿到结果摘要，再用 `Command(resume=summary)` 把结果喂回外层 Agent，让 AI 基于真实执行结果继续回答用户。

## 04 审批单：不只是内存里的一个状态

审批在早期版本是内存实现，重启就丢。现在审批单持久化到 `approvals.db`，每条记录包含：

- 审批单 ID；
- 会话、员工、发起用户；
- 触发工具和参数；
- 内层线程 ID；
- 状态：pending / approve / reject；
- 创建时间和过期时间。

治理规则也补上了：

- `APPROVAL_TTL_SECONDS` 控制过期时间，到期自动拒绝；
- `APPROVAL_PENDING_LIMIT` 限制待审批数量，防止审批积压拖垮流程；
- 审批接口有鉴权，普通用户只能处理自己会话产生的审批单，管理员可以统一处理；
- 审批决策接口返回 SSE 流，审批人提交后能实时看到 Agent 继续执行。

## 05 一次退款审批的完整旅程

假设用户向客服小苏申请退款，把链路完整走一遍：

1. 用户说"我要退款"；
2. 小苏调用 `start_refund(order_id, reason)`；
3. 内层状态机启动：校验订单；
4. 订单有效，计算退款金额；
5. 状态机到达 `await_approval` 节点，调用 `interrupt()` 挂起；
6. 外层 Agent 收到中断，创建审批单，前端弹出审批卡片；
7. 管理员在审批中心看到"订单 O12345 申请退款 399 元"，点击批准；
8. 系统恢复内层状态机，执行退款，生成退款单号；
9. 系统把退款结果作为工具返回值恢复外层 Agent；
10. 小苏把退款单号和到账时间告诉用户。

全程没有一步是"模型假装完成"，也没有"人批完就断线"。

## 06 设计经验

从这套实现里可以提炼几条通用经验：

**审批要长在流程里，而不是贴在流程外。** 状态机中的审批节点让每一步状态都可查、可恢复、可追踪；外层拦截只能处理"工具级确认"，处理不了"流程中间决策"。

**不要双重拦截。** 退款审批内化后，系统通过迁移把 `start_refund` 的外层审批 gate 撤掉了，避免同一次退款触发两次审批。

**线程 ID 要确定性派生。** 用订单 ID 加原因哈希派生内层线程，而不是依赖随机值，这样重启后审批恢复仍然能定位到同一次运行。

**审批状态必须可治理。** 落库、过期、数量上限、权限校验，这四件事决定了审批中心能不能真正投入运营。

## 07 边界与展望

当前退款流程中的订单数据还是演示 mock，真实环境需要把校验订单、查金额接到业务系统。审批决策的 resume 协议目前覆盖轻量审批和退款两种形态，未来需要通用化，支持更多带分支、嵌套审批的业务流程。

人机协同的终局不是"AI 申请、人审批"，而是企业可以配置"什么动作自动放行、什么动作必须人工、什么动作需要双人复核"。UniEmployee 的架构已经为这条路留好了位置。
