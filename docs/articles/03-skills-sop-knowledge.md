# 技能、SOP 与知识库：AI 如何不靠记忆工作

> 系列文章第三篇
> 2026-08-10，基于 UniEmployee 当前源码分析

大模型最大的优点和最大的缺点同源：它记住了海量知识，但也可能把记忆当成事实说出来。企业场景里，这不是"偶尔幻觉"的问题，而是合规和业务正确性问题：产品参数说错会引发客诉，制度条款说错会造成纠纷，经营口径说错会误导决策。

UniEmployee 的答案是让 AI 形成三条纪律：**技能告诉你该怎么做，SOP 约束流程怎么走，知识库提供事实依据。** 这一篇拆开看这三层是怎么实现的。

## 01 模型不该凭记忆回答业务问题

通用聊天机器人的工作方式是"模型知道什么就说什么"。UniEmployee 的工作方式反过来：模型先判断该用哪个技能，技能要求它读规程、查知识库、跑工具，最后基于证据作答。

这样做有三个直接收益：

1. 事实来自企业自己的资料，而不是模型训练数据；
2. 回答可以追溯到依据，审计友好；
3. 资料更新后立即生效，不需要等模型重新训练。

## 02 技能：双通道设计

一个技能就是一个目录，里面有一份标准化的 `SKILL.md`：

```yaml
---
name: product-faq
description: 产品知识问答技能。当用户咨询产品参数、价格、保修等产品相关信息时使用。
---

# 产品知识问答规程

## 适用范围
用户询问产品规格、价格、保修、物流、积分等问题时使用本技能。

## 执行步骤
1. 先确认用户问的是哪个产品；
2. 调用 kb_search 检索知识库；
3. 仅依据检索结果回答，末尾标注来源；
4. 检索不到时明确告知需要核实，禁止编造。
```

编译时，系统只把"触发条件 + 规程路径"拼进 system_prompt，形成技能路由：

```text
## 技能路由（确定性激活）
当用户消息满足某技能的触发条件时，必须先 read_file 查阅完整规程再执行：

### product-faq
触发条件：用户咨询产品参数、价格、保修时使用。
规程路径：/skills/product-faq/SKILL.md
```

运行时，模型命中技能后通过 `read_file` 读取完整规程。这就像一个员工把岗位手册放在手边：平时不用背，办事前翻开看。

这种设计的核心是"路由摘要很轻、规程全文很全"。摘要每轮都进上下文，成本可控；全文按需读取，不会把几千字塞进每次调用。

## 03 技能可以热更新

技能内容变更有两种入口：

- 管理员上传技能 zip 包；
- 直接在技能编辑弹窗里修改 SKILL.md。

变更后系统只调用 `refresh_skills_for_employees()` 刷新 Store 中的技能内容，不触发 Agent 重编译。原因很直接：Agent 结构没有变，变的只是它运行时能读到的规程。

技能 Store 还按用户视角做了命名空间隔离。普通用户的有效技能来自"模板 + 用户覆盖"，不同用户看到的技能集合可以不同，互不覆盖。

## 04 SOP：软性规程与刚性流程

SOP 是比技能更接近"流程"的约束，UniEmployee 把它分成两类：

### 软性 SOP：模型按规程执行

比如投诉处理 SOP 会被完整写入 Store 的 `/sops/sop_complaint.md`，system_prompt 里只放一条摘要和路径。模型读到"用户表达不满时必须先读投诉处理规程"后，会按步骤执行：安抚、核实、分类定级、登记工单、给出方案。

### 刚性 SOP：状态机强制执行

退款是刚性流程，只用提示词约束不够。它被实现为 LangGraph StateGraph：

```text
校验订单 -> 计算退款金额 -> 等待人工审批 -> 执行退款
```

每一步都是图里的节点，审批是一个显式挂起节点。模型无法跳过校验、无法绕过审批，流程的确定性由代码保证，而不是靠模型自觉。

这就是 UniEmployee 对"规程"的理解：**能靠规则说清楚的用 SKILL.md，能靠代码固化的用状态机，两者的结合才是可靠的 SOP。**

## 05 知识库：事实从哪来

知识库是技能的"弹药库"。当前实现通过 `kb_search` 闭包工具完成：

- 运行时读取员工有效配置中的知识库映射；
- 按映射的 RAGFlow dataset 检索；
- 返回带来源和相似度的片段；
- 未配置 RAGFlow 时明确提示，不假装能检索。

关键设计是"动态查询"：`kb_search` 不持有编译期快照，每次调用都从 catalog.db 读最新配置。管理员给员工增删知识库后，不用重编译 Agent，下一次提问就会命中新配置。

检索结果的格式也刻意设计成"可引用"：

```text
[1] 来源：文档名 | 相似度：0.83
文档原文片段...
```

员工回答时标注依据，用户和管理员都能核验。

## 06 一个完整的执行例子

用户向客服小苏投诉产品故障。一次对话里可能发生这些事：

1. 模型识别到投诉意图，system_prompt 中的技能路由提示它调用 `complaint-handling`；
2. 模型先 `read_file` 读取投诉处理 SKILL.md；
3. 规程要求调用 `kb_search` 查该产品是否有已知问题；
4. 规程要求核实订单，模型调用 CRM 连接器查询订单；
5. 规程要求登记工单，模型调用 `create_ticket`；
6. 如果用户提出退款，模型调用 `start_refund`，流程进入状态机并停在人工审批节点；
7. 审批通过后，模型继续把退款结果告诉用户。

每一步都在 Trace 里留下记录。这不是"模型想起了什么"，而是一套被规程驱动的执行。

## 07 治理与边界

技能、SOP、知识库要真正可靠，还需要内容治理：

- **内容所有权**：知识库要有明确负责人，来源文档要可回溯；
- **更新闭环**：制度变更后要同步更新资料，否则 AI 会引用旧口径；
- **不滥用上下文**：全文进 prompt 是错误方向，路由摘要 + 按需读取才是可持续的；
- **权限**：当前版本的知识库按员工分配，后续需要进一步支持角色级和用户级可见性，避免"知道不等于有权"。

下一篇，我们讲一个更前沿的能力：业务本体。它让 AI 不仅知道"文档写了什么"，还知道"企业的客户、订单、项目和员工之间是什么关系"。
