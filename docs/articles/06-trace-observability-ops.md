# Trace 与运营：让 AI 从黑箱变成可审计的劳动力

> 系列文章第六篇
> 2026-08-10，基于 UniEmployee 当前源码分析

AI 应用最让企业担心的问题不是"它不会干活"，而是"它干活时我什么都不知道"。模型为什么给出这个答案？它查了哪些资料？调了哪个工具？花了多少 token？出了问题能不能回放？

UniEmployee 从第一天就把可观测性当成第一等公民：每次对话、每次审批恢复都是一次 run，从模型调用到工具执行全部落库，前端实时展示，管理员可以回放。

## 01 一次 run 记录什么

Trace 使用独立的 `traces.db`，包含两张表：

**runs 表**记录一次执行的概要：

- run_id、会话 ID、员工 ID、用户 ID；
- 类型：message（新消息）或 resume（审批恢复）；
- 输入预览；
- 状态：running / done / error / interrupted；
- 模型调用次数、工具调用次数、总 token 数；
- 开始时间、结束时间、总耗时；
- 错误信息。

**events 表**记录执行中的每个步骤：

- 事件类型：llm 或 tool；
- 名称（模型名或工具名）；
- 状态：ok / error / running；
- 输入、输出（裁剪到安全长度）；
- token 数、耗时、开始时间。

这些数据回答了运营最关心的四个问题：AI 调了什么、花了多少钱、用了多久、成功没有。

## 02 事件是怎么被捕获的

Trace 没有侵入业务代码。它实现了一个 LangChain `AsyncCallbackHandler`，注入到每次 agent 执行的 callbacks 中。模型开始、模型结束、模型错误、工具开始、工具结束都会触发回调，再写入 traces.db。

几个实现细节值得注意：

- 每个 LangChain run_id 会配对 start/end，保证异步调用不会串数据；
- 输入输出统一裁剪，默认 2000 字符，避免数据库无限膨胀；
- 所有写库操作都吞异常：Trace 失败绝不阻塞对话；
- `run_inline = True` 让回调在主事件循环内执行，SQLite 写入足够快，避免线程切换开销。

## 03 用户看到的实时执行过程

前端聊天页通过 SSE 实时接收事件，而不是等 AI 说完才看到结果：

```text
stage         员工已加载、SOP、技能等阶段状态
thinking      模型的思考过程
todos         子任务清单
tool          工具开始调用和完成状态
subagent      子代理开始和完成状态
token         AI 回答的流式文字
approval_required  需要人工审批
error         错误码 + 用户可读提示
```

执行过程页面按会话展示 run 列表，展开后可以看到每一步 LLM 调用的输入输出、工具调用的参数结果、token 和耗时。管理员还可以在首页看到 token 统计。

错误处理也做了分级。SSE 不会把内部异常原文抛给前端，而是映射为稳定的错误码：

| 错误码 | 含义 |
| --- | --- |
| timeout | 模型或工具响应超时 |
| rate_limit | 请求过于频繁或触发限额 |
| context_length | 上下文过长 |
| auth | 模型或工具鉴权失败 |
| internal_error | 内部执行错误 |

前端使用 AbortController 管理流式请求，页面卸载或发起新请求时主动断开旧连接，避免服务端挂起时连接不释放。

## 04 从 Trace 到会话恢复

Trace 不只是事后审计，还参与运行时恢复。服务重启时会扫描 checkpointer 中的历史线程，重建会话清单。员工归属的判断有三级兜底：

1. 优先读线程元数据中写入的 employee_id；
2. 没有元数据时查 Trace 记录；
3. 老数据最后用技能名做近似匹配。

新会话的首条消息还会触发标题生成：系统用模型把首轮对话提炼成不超过 16 字的中文标题。历史记录因此可读、可检索、可管理。

## 05 运维配套

围绕 Trace 还有一套基础运维设施：

- `/health` 健康检查，逐一验证所有 SQLite 库可连接，返回版本和数据库状态；
- 结构化日志，每个请求带 `X-Request-Id`，便于跨模块定位；
- `scripts/backup.sh` 备份全部业务数据库，支持保留份数控制；
- 应用退出时统一关闭 MCP client，避免 stdio 子进程残留；
- `APP_DATA_DIR` 统一控制数据目录，容器里挂载持久卷。

这套设施保证平台在单机演示之外，也有被运维接管的基础。

## 06 从 Trace 到运营闭环

有了数据，运营才能形成闭环：

**成本管理**：按 run 统计 token、按模型调用定位高消耗环节；

**质量改进**：回放错误答案，看模型是没读技能、没查知识库，还是工具参数传错；

**故障排查**：审批卡住、工具失败、模型超时，都可以从事件时间线定位；

**审计合规**：每一次 AI 决策都有"为什么"的证据链，配合来源标注构成完整审计记录；

**员工评估**：同一岗位的多个数字员工配置可以通过 Trace 对比效果，决定上线哪个版本。

## 07 边界与展望

当前 Trace 已经覆盖"对话 + 审批恢复"主链路，但离完整运营中心还有距离：

- 前端执行过程页是基础时间线，还没做错误分布、调用树、子代理嵌套视图；
- 运行时指标（并发数、队列长度、MCP 进程数、缓存命中率）还没有统一上报；
- token 统计目前是全局维度，按用户和员工维度的配额治理在规划中；
- 模型名、错误分类、输入输出裁剪粒度需要继续完善。

路线图里已经有"运维中心"和"Trace 可视化增强"两个专项。方向很明确：从"可回放"走向"可度量、可预警、可治理"。
