# UniEmployee × DeerFlow：以业务收益为依据的迭代决策方案

> 评估基线：UniEmployee 当前检出 `0951e32`（`codex/evaluation-workbench`）；本地 DeerFlow `fc9fb2de`；源码核对日期 2026-09-26。本文是**源码能力与投资判断**，不是客户环境的故障统计或收益承诺。业务指标、阈值和工期均须由试点负责人确认。

按优先级逐项核验的实时结论见[能力验证台账](./deerflow-capability-verification-log.md)；方案中的“存在缺口”不自动等于“应立即开发”，需要对应证据与验收条件。

## 1. 建议决策

**先选择一个可核验的只读业务场景，用现有平台跑通真实数据、评测和人工兜底；再按试点中实际出现的损失，选择 DeerFlow 的运行治理能力。** 当前最值得投入的不是增加 Agent 功能数量，而是让已有功能产生可信、可重复、可交付的结果。

| 顺序 | 投入项 | 目前可确认的不足 | 做成后的直接价值 | 决策 |
|---|---|---|---|---|
| P0 | 单场景真实数据接入及演示数据隔离 | 开发环境仍播种演示实体；生产模式新库已加播种与实验 CRM 门禁，但旧库迁移、其他演示资产和真实数据权限闭环未完成 | 让回答可用于业务判断，避免把模拟客户/告警当成事实 | 试点前做 |
| P0 | 用现有评测工作台建立业务用例和发布门槛 | 已能运行、留痕和人工判定用例；缺的是经业务方确认的用例、风险分层和放行流程 | 配置变更可被量化比较，减少错误答案进入试点 | 与真实数据接入同步做 |
| P0 | 试点最小生产保障 | 7 库 + `workspace` 已在隔离环境恢复通过；一致性备份、生产凭据和执行边界及业务 RPO/RTO 仍待核验 | 避免结果文件丢失、数据泄露或试点被安全问题叫停 | 按试点实际数据和工具范围做 |
| P1（条件触发） | 长任务独立运行及重新连接 | 已实现单进程后台运行、事件持久化和断线重连；跨进程接管、服务重启后续跑和真实长任务收益尚未验收 | 报告、调研等长任务离开页面后仍能完成，降低重跑成本 | 单实例技术闭环已做；扩展能力按业务损失触发 |
| P1（条件触发） | 定时任务执行记录、恢复与重试 | 已有逐次账本、Cron/Webhook 幂等、超时中断发现和人工重跑；仍是进程内执行、停机漏点仅补一次，未测真实任务收益 | 可定位某次触发、避免同一 Webhook 重复运行，并由管理员评估后重跑，减少重复副作用与排障成本 | 单实例技术闭环已完成；业务正式无人值守前仍需 Docker 演练和 owner 确认时效政策 |
| P1（条件触发） | 模型准入、超时和成本预算 | 已加可配置的单进程、按模型 Agent 准入、有限排队、拒绝指标和 OpenAI 兼容单次请求超时；默认准入阀关闭。费用硬预算、跨进程配额与业务基线未完成 | 限制单实例突发并发，排队过久时快速反馈；后续按真实价格和任务成本设置预算 | 技术护栏部分已做；金额预算待模型价格/业务阈值/实际用量证据，不先设猜测阈值 |
| P2（条件触发） | 子代理次数与并发上限 | 已有按配置启用的每次 Agent run 委派次数和顶层并发上限；默认关闭；general-purpose 子代理内部递归尚未完全覆盖，且未有真实调用基线 | 控制异常委派放大的延时和 token 消耗，并让额度耗尽成为可见反馈 | 单实例技术闭环部分已做；取 Trace 基线、完成 Docker 超限演练后再决定默认值与扩展边界 |
| 暂缓 | 自动目标续跑、手动压缩、复杂记忆、插件生态、全面多实例 | 现阶段没有对应业务损失证据；平台已有摘要/记忆、MCP、单节点试点能力 | 在长流程、长上下文或扩容需求成立后才有增量价值 | 保留启动条件，不排进近期承诺 |

P0 表示**启动所选试点的必要条件**，不表示全部平台功能都要同时完善。P1/P2 是候选投资，不是预先批准的开发清单。

### 若当前没有可对接的真实业务系统

先走一条**最小 API 服务验证轨道**：在 UniEmployee 的同级目录部署独立 Docker Compose 服务，明确标为“实验业务系统”，使用独立 SQLite 数据文件和持久化卷。它不与 UniEmployee 共用进程或数据库；接口只覆盖客户、客服 Case 两类对象：`GET /customers/{id}`、`GET /cases?customer_id=...`、`GET /cases/{id}`。为源系统的人工变更提供管理员写入接口，所有返回包含记录 ID、更新时间和来源；UniEmployee 只使用独立的只读 API Key。第二阶段如需验证人工审批后的业务写入，再把 `POST /cases` 接入 Agent，并补幂等键与回读确认。

这比立即部署完整 CRM 更快地检验**跨进程/跨容器调用、身份凭据、真实持久化、数据更新、空结果、服务故障和审批边界**。现有 CRM mock 只是同一代码库里的内存字典，[`create_ticket`](../../backend/app/tools/kb.py) 也只返回编号，无法证明外部系统已经收到工单。最小 API 服务必须保持独立存储和明确状态流转，否则只是给 mock 增加 HTTP 外壳。

实验链路：在实验业务系统新增/修改客户和 Case → UniEmployee 的只读 MCP 连接器调用 HTTP API → “小小”回答当前状态并返回来源、记录 ID 和更新时间 → 评测工作台核对正确、空结果、无权限和服务不可用四类结果。合成数据只能证明**集成链路**，不能证明真实 CRM 的复杂权限、业务流程、用户采纳或 ROI。

当最小 API 服务验证完成、确实需要更接近实际业务系统的页面、角色和流程时，再部署 [EspoCRM](https://github.com/espocrm/espocrm)，其[官方 Docker 部署](https://docs.espocrm.com/administration/docker/installation/)、[REST API](https://docs.espocrm.com/development/api/)和[角色权限](https://docs.espocrm.com/administration/roles-management/)可用于第二层兼容性验证。其他候选见[本地开源业务系统对接候选](./open-source-business-systems-research.md)。两层实验的验收结论应分开记录；都不能替代真实业务试点。

## 2. 决策依据：两个架构的关系

UniEmployee 的核心是“**可配置数字员工平台**”：catalog 中配置员工、知识、工具、SOP 和授权，运行时在 [`compiler.py`](../../backend/app/compiler.py) 调用 `deepagents.create_deep_agent`，通过 FastAPI/SSE 服务、LangGraph checkpoint、Store、审批和 Trace 承载企业流程。DeerFlow 更偏“**长任务 Agent harness**”：在 [lead agent](https://github.com/bytedance/deer-flow/blob/fc9fb2de/backend/packages/harness/deerflow/agents/lead_agent/agent.py) 用 LangChain `create_agent` 及大量自定义 middleware，外部有 [RunManager](https://github.com/bytedance/deer-flow/blob/fc9fb2de/backend/packages/harness/deerflow/runtime/runs/manager.py)、运行 worker、目标续跑、模型准入和委派治理。

两者都使用 LangChain/LangGraph 生态，因此**模型、消息、工具、checkpoint 等概念可以映射**；但上层 Agent 装配与生命周期不同。UniEmployee 当前依赖 `deepagents==0.7.13`、`langgraph==1.2.11`，DeerFlow 的 harness 依赖自己的状态、事件、middleware 和 gateway。直接搬运 DeerFlow 的 worker 或 middleware，可能破坏 UniEmployee 的工具授权、审批恢复、Store 命名空间及 SSE 协议。**可行路线是保持 deepagents 主链不变，在平台边界实现被数据证明需要的运行治理；只有单项能力无法在当前接口稳定实现时，才单独评估更换 Agent 装配层。**

迁移可行性分级：真实数据接入、现有评测运营、文件备份属于平台/运维层，**高**；独立运行、调度恢复、模型准入属于运行时边界，**中**；完整移植 DeerFlow 的 goal loop、middleware 栈或 RunManager，**低到中**，需要逐项证明兼容性。共享框架并不等于组件可直接复制。

工具装配的单项源码对比、DeerFlow 当前启用工具清单和运行时核验，以及 UniEmployee 应否引入延迟 schema 发现，见[DeerFlow 工具加载机制与 UniEmployee 借鉴评估](./deerflow-tool-loading-comparison.md)。当前建议先补工具清单诊断与 MCP 生命周期反馈；CRM Lab 工具规模尚不足以支持立即开发 `tool_search` 类能力。

网页搜索后读取正文、DeerFlow 的 Agent 浏览器工具与用户侧 Live Browser 面板，以及 UniEmployee 是否需要迁移，见[网页抓取与浏览器交付评估](./deerflow-web-crawl-browser-migration.md)。当前建议先核验既有 Playwright MCP 和网页来源评测；Live Browser 只有在静态截图无法满足真实业务接管需求时再立项。

其余 DeerFlow 候选能力（远端工具结果净化、子代理行动凭据、Skill 包审查、批量子代理、项目文档上下文、插件/BlobStore）与 UniEmployee 已有能力的重叠及投资触发条件，见[可借鉴能力补充评估](./deerflow-additional-capabilities-review.md)。新评估优先关注外部 MCP/web 输出的信任标记与工具结果处理；批次代理、项目空间、插件宿主和多实例内容存储继续等业务或扩容证据。

## 3. 每项投资的价值、验收与启动条件

### A. 真实数据与演示隔离（P0）

- **现状证据**：开发模式启动时调用多个 `seed_*_demo_if_empty()`；`APP_ENV=production` 现已跳过这些演示本体实例，并禁止 `crm`/`crm_lab` 实验连接器播种和加载，见[`demo_isolation.py`](../../backend/app/demo_isolation.py)。[`crm_server.py`](../../backend/app/connectors/crm_server.py) 仍是开发环境使用的模拟 CRM。新库生产播种隔离已在临时 PostgreSQL 验证；旧库演示记录、workspace/RAGFlow 资产及真实业务数据授权仍未完成。
- **为何要改**：使用者关心的是“能否引用最新、授权的事实完成工作”。把模拟数据接到真实界面会产生误判风险；即使 Agent 推理正确，数据不真也没有业务收益。
- **建议做法**：选择一个场景（优先候选：产品/制度问答与工单分流；若业务方能提供告警、拓扑、工单的权威只读源，也可选故障影响分析），明确数据 owner、更新时间、权限和人工接管。生产配置禁止演示种子，模拟连接器显式标记且不能误绑定生产员工。只为这个场景开发最小只读连接器。
- **预期价值**：员工回答可被核验和追责；减少查资料、跨系统核对所需时间。收益按“每周有效任务量 × 单任务节省分钟 × 实际采纳率”估算，减去复核时间、模型和运维成本。**当前没有用户数据，不能写出已节省多少人时。**
- **验收/停止条件**：每条关键答案可回到授权来源和数据时间；演示实体在生产新环境为零；业务方抽检的错误/过期引用有记录和修复责任人。如果真实数据不可用或人工复核成本高于节省时间，暂停扩面。

### B. 业务评测和发布门槛（P0，利用现有实现）

- **现状证据**：当前分支已有 [`evaluation_sets.py`](../../backend/app/evaluation_sets.py)、[`admin.py`](../../backend/app/routes/admin.py) 的用例集、真实员工运行、结果、Trace 和人工 `pass/fail/needs_review` 判定，前端 [`AdminEvaluation.vue`](../../frontend/src/views/AdminEvaluation.vue) 有评测界面。单次最多 25 个启用用例，任务通过 FastAPI `BackgroundTasks` 在应用进程执行。它**不是零基础缺口**，也**不是自动质量判定或耐故障批处理平台**。
- **本地技术基线已补充**：在 CRM Lab 合成数据上为 `xiaoxiao` 建立了 3 例只读基准，覆盖客户全景、Case 详情和无匹配结果；3/3 经回答及 Trace 人工核对后通过。每例只调用 CRM Lab 工具，没有知识库/本体调用。完整运行 ID、结果、Trace 和 token 统计见[集成验证记录](./crm-lab-integration-validation.md#现有评测工作台回归基线)。这证明工作台能支撑本地技术回归，不等于业务用例签收，也不构成真实数据的发布门槛。
- **为何要改**：有功能页面但没有经业务方确认的高风险问法，无法判断一次 prompt、工具或模型改动是否改善了任务完成率。
- **建议做法**：每个试点员工先收集真实任务和失败样例，按“常见/边界/无答案/过期数据/越权/高风险”分类；每个用例记录判定标准、风险级别、业务负责人。用现有工作台分批跑（每批 ≤25），评审结果与配置 hash、Trace 绑定。先形成手工发布门槛；当运行频率和用例规模确实超过人工能力时，再考虑自动判分、CI 和持久化评测 worker。
- **预期价值**：减少回归和错误上线；让优化方向来自失败样本而非主观感觉。可比较改动前后的关键任务通过率、转人工率、引用准确率和单任务成本。
- **验收/停止条件**：高风险失败单独列出，关键用例逐条有业务 owner 签收；同一批用例可以比较两个配置版本。建议阈值由业务方按损失设定；不能以总体平均通过率掩盖越权或严重误答。连续迭代若没有改善，应回到数据质量/业务流程问题，而不是继续堆 Agent 功能。

### C. 试点最小生产保障（P0，范围随试点缩放）

- **现状证据**：[`backup.sh`](../../scripts/backup.sh) 只打包 7 个 PostgreSQL 业务库；产物文件在 `workspace`。[`compiler.py`](../../backend/app/compiler.py) 的 `local_shell` 使用 `inherit_env=True`，而 `sandbox` 生产模式未启用时会拒绝回退。已有工具护栏、审批和 OIDC，不能据此假设任何连接器凭据、文件和外部数据源都经过生产验证。
- **为何要改**：试点一旦产生报告/附件和真实数据，恢复和凭据隔离会直接影响持续使用与审批通过；这些问题造成的损失通常高于新增一个 Agent 能力。
- **建议做法**：针对试点实际会用的文件和数据库做联合备份、恢复演练；生产员工最小工具授权，业务系统只读账号，执行型员工优先启用沙箱；检查连接器子进程与 shell 可见的密钥、Trace 脱敏及日志保留。若试点无文件产物，可先不建设复杂对象存储，但要明确恢复边界。
- **预期价值**：缩短故障后的恢复时间，降低真实数据泄露/误操作概率，使业务部门敢把日常任务交给平台。
- **验收/停止条件**：业务方批准的 RPO/RTO 有恢复演练记录；试点凭据不暴露给无授权员工和工具；高风险操作要么不可用，要么经过现有审批与审计。

### D. 长任务独立运行与重新连接（P1，条件触发；借鉴 DeerFlow RunManager）

- **现状证据**：改造前 streaming.py 在 SSE 连接的执行链内调用 agent.astream，断开会取消执行。当前已新增 agent_runs.py：持久化运行状态与事件，worker 独立于 HTTP 订阅运行，支持按事件序号重连、显式取消、HITL 恢复和进程启动时将遗留运行收敛为 abandoned。详见验证台账。
- **为何要改**：对 30 秒问答，独立 worker 增加系统复杂度却少有收益；对几分钟的报告/调研/多工具任务，切页或网络波动导致重跑，才有明确损失。
- **已实现范围**：Web 消息、审批恢复在一个应用进程内由后台任务执行，浏览器断开或切页只取消订阅，页面重开后从数据库事件游标续接。当前每个会话只允许一个活跃运行，事件默认保留 7 天。进程重启会将运行标记为 abandoned，不会从 checkpoint 自动续跑；多 worker 的租约、跨实例取消和事件保留策略需要后续设计并实测。
- **预期价值**：长任务成功交付率提高；用户不必守着页面，重复模型费用下降。**衡量**：断流后仍完成率、因断流重跑率、P95 完成时间、每个完成任务的 token 成本。
- **启动/退出**：代码级单实例能力已实现；生产推广仍需隔离 runtime 的断网实测、PostgreSQL 验收、长任务断流/重连率、断流后完成率与 token 成本数据。若主要是短问答，先不投入多实例运行管理。

### E. 定时任务可靠性（P1，条件触发）

- **现状证据**：[`scheduler.py`](../../backend/app/scheduler.py) 是应用内循环，利用 `next_fire_at` CAS 抢占；停机错过的触发点仍只补跑一次。改造前 [`automations.py`](../../backend/app/automations.py) 仅保留最近状态；当前已新增 `automation_executions` 逐次账本、Cron 计划时间键、Webhook/人工重跑幂等键、20 秒心跳、120 秒超时中断标记及管理员执行历史/人工重跑。
- **为何要改**：日报、告警汇总等任务一旦承担交付时效，重复运行会重复调用工具，漏跑则需人工查日志判断是否应补。逐次记录解决“哪一次触发、进入哪个会话、在哪里失败”；幂等键降低上游超时重投导致的重复 Agent 任务；超时标记提供人工判断入口。
- **实现选择**：不自动重试可能已执行部分副作用的任务；恢复不会重复保存事件 payload，事件任务由管理员重跑时重新提供 payload。外部 Webhook 必须使用稳定 `Idempotency-Key`；记录默认保留 90 天。单实例技术闭环及 SQLite/PostgreSQL 测试通过，见[能力验证台账](./deerflow-capability-verification-log.md#p1-e自动化任务执行账本幂等与人工恢复)。
- **预期价值**：缩短失败定位和人工补跑时间，降低重复通知/写入风险。**衡量**：按期交付率、漏跑/重复率、人工补跑时长、误触发副作用数。尚无真实任务数据，不能宣称收益已实现。
- **剩余边界**：应用进程内执行；进程崩溃只标记 `interrupted`，不会从 checkpoint 自动续跑；停机漏点合并补跑一次。是否逐点补跑、是否引入队列和 worker，等真实任务的 SLA、漏跑损失与频率确定后再决定。
- **启动/退出**：技术功能已按持续验证目标实现；正式无人值守前必须完成 Docker Webhook 同键重放/查看/人工重跑演练，并由业务 owner 决定时效及补跑政策。没有业务 SLA 时不扩大成独立调度服务。

### F. 模型准入、委派预算与长上下文（P1/P2，分别触发）

1. **模型准入（P1）**：DeerFlow 的 [RequestAdmission](https://github.com/bytedance/deer-flow/blob/fc9fb2de/backend/packages/harness/deerflow/models/request_admission.py) 有并发/排队边界。UniEmployee 已新增 [`model_admission.py`](../../backend/app/model_admission.py)：按模型限制 Agent run 的单进程并发，队列人数和等待上限可配置；满载会记 Trace 并快速拒绝。配置 `MODEL_MAX_CONCURRENT` 大于 0 才启用，默认关闭以免没有容量基线就限流；`MODEL_REQUEST_TIMEOUT_SEC` 为 OpenAI 兼容单次 API 请求设置超时；管理员可从 `/api/admin/ai-models/admission` 查看本进程活跃、排队、拒绝数和等待统计。它控制的是 Agent run 占槽（包括工具等待），不是每个独立 LLM 子调用的信号量；多副本配额不共享。已有 token Trace 不含可靠的货币价格/预算，先采集模型、员工、任务的 token/耗时/429/超时和费率，再由 owner 设硬预算。技术验证证据见[能力验证台账](./deerflow-capability-verification-log.md#p1-f模型准入超时与成本预算)。
2. **子代理预算（P2）**：UniEmployee 已加 [`subagent_budget.py`](../../backend/app/subagent_budget.py)，基于 deepagents 依赖的公开 LangChain `AgentMiddleware` 限制每次 run 的 `task` 总调用数和主 Agent 顶层并发；到限值后 ToolMessage 会告知主 Agent。默认 `SUBAGENT_MAX_CALLS_PER_RUN=0` 与 `SUBAGENT_MAX_CONCURRENT_PER_RUN=0`，必须结合真实 trace 手动启用。显式配置子代理共享总次数，deepagents 自动注入 general-purpose 子代理的内部递归尚未全部覆盖；并发 semaphore 为防递归死锁只放在主 Agent 顶层 task。价值是控制异常执行；普通任务若几乎不用子代理，收益很小。验收台账记录了测试范围与 Docker/Trace 剩余项。
3. **目标自动续跑与手动上下文压缩（暂缓）**：DeerFlow 有 [目标评估/续跑](https://github.com/bytedance/deer-flow/blob/fc9fb2de/backend/packages/harness/deerflow/runtime/goal.py) 和手动 compact 接口。UniEmployee 已通过 deepagents 使用摘要及 Store 记忆。只有出现“任务多次需要用户说继续”或“长会话因上下文不足失败”的可复现样本，才分别评估。自动续跑需要额外目标判定、无进展熔断、token/时间上限和审批边界；先做运行与预算治理，再做自动续跑。价值分别是减少人工催促、降低长会话失败；风险是无意义续跑和额外模型费用。

### G. 渠道、记忆、插件、多实例（暂缓或随需求触发）

UniEmployee 已有平台内 Web/IM 频道架构、按用户和员工隔离的 Store 记忆、MCP 接入；DeerFlow 的能力更丰富，但不能由此推断 UniEmployee 用户缺少渠道或记忆。只有当试点用户主要在企业 IM 办公且 Web 采纳率受阻时，接**一个**实际渠道，衡量活跃率和任务完成量。只有当重复提问可归因于记忆缺失时，做结构化记忆质量与遗忘策略。只有多个独立团队确实需要同类连接器时，再投资插件市场/扩展 API。只有单实例容量或可用性达不到书面目标时，再解决缓存失效、MCP 生命周期、共享文件、SSE/worker 和调度的跨实例一致性；DeerFlow 的进程内准入也不能自动解决分布式治理。

## 4. 技术落地边界与可行性

下表是**立项后的最小实现**，用于估算和分工，不代表 P1/P2 已决定开发。工作量按单名熟悉仓库的后端工程师估算，不含业务数据授权、标注、部署审批和外部系统配合；“周”是量级，不是承诺日期。

| 投入项 | 最小技术改动 | 对现有链路的要求 | 可行性 / 粗估 / 主要风险 |
|---|---|---|---|
| A 真实数据与演示隔离 | 在 `main.py` 增加生产种子策略；为所选业务系统实现一个只读连接器，带来源、更新时间和授权映射；生产资源中心标记演示项 | 保持 catalog 配置方式、现有 `kb_search`/MCP 或分析师只读查询路径 | 高 / 2–4 周开发；真实系统 API、权限和数据质量通常是关键路径 |
| B 业务评测 | 在现有 `evaluation_suites` 填入经业务方确认的用例；补风险等级、评审责任人、版本对照导出和人工发布记录，先不重写执行器 | 复用现有 Trace、配置 hash、人工 grade；25 条限制按批次运行 | 高 / 1–2 周开发加持续标注；`BackgroundTasks` 进程中断会留下未完成运行，若成为常态再迁移 worker |
| C 生产保障 | 备份脚本覆盖 DB + `workspace`，记录同一恢复点；生产配置检查与只读服务账号；按需启用 OpenSandbox | 不绕过现有护栏、审批、文件 ACL 和 `tenant_id` | 高 / 1–3 周开发运维；备份一致性、密钥传递和真实恢复演练需共同验收 |
| D 长任务独立运行 | 新增 `runs`（状态、租约、owner、取消标记）和 `run_events`（单调序号、事件类型、有限保留）；`POST` 启动、`GET` 状态、`GET` 事件流、`POST` 取消；worker 执行 `agent.astream`，SSE 按事件序号重连 | 现有会话仍是业务对象，`run_id` 是一次执行；沿用 checkpoint；同一会话限制并发写；HITL `interrupt`/resume 必须对应同一运行状态；完成/失败/取消均收尾 Trace | 中 / 4–8 周；最大风险是 checkpoint 并发、SSE 事件重复/丢失与审批恢复；先做单实例原型验证 |
| E 自动化可靠性 | 已实现 `automation_executions`（触发键、状态、会话、错误、重跑关系）、唯一键去重、心跳超时发现和管理员人工重跑；后续可按 SLA 将执行交给 D 的 worker | 保留 cron 解析与 CAS；不自动重试有副作用工具；Webhook 上游要保存并重用 `Idempotency-Key` | 单实例技术改造已完成；剩余跨进程恢复与逐点补跑取决于业务 SLA，当前不预建独立队列 |
| F 模型准入 | 在模型调用入口按模型/员工配置并发、排队时长和成本预算；暴露排队、拒绝及 429 指标 | 不改变员工配置与审批；排队超时返回可理解的错误 | 中 / 2–3 周；必须确认 deepagents 所用模型对象的包装/限流注入点，多实例另需共享配额 |
| 子代理预算 | 在现有子代理调用边界记录和限制每轮/每任务委派次数及并发 | 不用 prompt 当硬约束，超限要可见且不产生半完成业务动作 | 中 / 2–4 周；deepagents 内置 `task` 工具调用边界需原型验证，不能直接套 DeerFlow middleware |
| 目标续跑 / 手动压缩 | 先做故障样本和 deepagents checkpoint 兼容性原型，再分别设计预算/无进展熔断或保留历史的摘要接口 | 先具备运行状态、取消、成本上限和人工审批边界 | 中低 / 4–8 周以上；可能需要 Agent 装配层改造，现阶段不估入计划 |

**接口原则**：先改平台自己的运行/模型边界，不修改第三方 `deepagents`/`langgraph` 源码。新增持久化记录必须携带 `tenant_id`、`employee_id`、`user_id` 和可追溯的 `trace_run_id`；回放事件需租户与会话授权。数据库迁移需同时验证 PostgreSQL 目标环境及当前测试 SQLite 路径。异步 worker 上线前，要设计服务重启后的 `queued/running` 收敛与消息保留期限，否则“已排队”不等于“可恢复”。

**明确依赖关系**：B 的真实业务用例依赖 A 的权威数据；D 的最小运行记录可独立于 E 实施，但 E 要保证运行交付通常应复用 D 的执行能力；目标续跑依赖 D 和 F 的取消/预算治理；多实例需要 D/E 的租约与事件持久化、配置缓存失效和文件共享方案。这样可以避免一次性重写 Agent 架构。

## 5. 执行节奏与投资门槛

| 阶段 | 交付物 | 放行依据 | 不达标时的动作 |
|---|---|---|---|
| L. 本地集成验证（当前无业务系统时） | 已在同级目录部署独立 CRM Lab Compose API；UniEmployee 有 4 个未默认指派的只读 MCP 工具。合成源数据变更、权限边界、故障反馈、宿主机和 Docker Agent SSE，以及现有评测工作台的 3 例基准均已运行；详见[验证记录](./crm-lab-integration-validation.md)。 | 容器健康、4 个 MCP 工具、SSE 对话和 3/3 只读评测用例均通过人工核对。合成数据只证明技术链路与本地回归能力，不代表真实业务准确率或 ROI。 | 本地技术验证阶段完成；下一步需由业务 owner 选定真实流程、提供授权数据和签收用例，之后才形成业务发布门槛 |
| 0. 业务选题与基线（建议 1–2 周） | 一个岗位/流程、责任人、现有人工耗时和质量基线、数据/权限清单 | 结果可核验、数据可授权、人工可接管 | 换场景；暂停运行时扩建 |
| 1. 可用试点（建议 3–6 周） | 真实只读源、演示隔离、关键评测集、生产最小保障 | 业务 owner 对关键用例和恢复边界签收 | 修数据和流程；缩小用户范围 |
| 2. 收益复盘（连续观察至少一个业务周期） | 任务完成率、人工接管率、节省净时间、错误损失、P95、成本和失败分类 | 净收益为正，严重错误在批准范围内 | 停止扩面，明确根因 |
| 3. 定向改造 | 只立项数据证明的 P1/P2 项，并建立改造前后对照 | 对应损失下降，收益覆盖开发及运维成本 | 回滚或停止该能力投资 |

工期只是单场景、已有开发/运维支持的**粗估**；数据授权、业务标注和真实系统对接通常决定实际周期。不要把上表周数作为交付承诺。对每项工程改造，采用同一投资判断：

> 年化净收益 ≈ 任务量 ×（节省人工时间 × 人工单位成本 + 降低的错误/漏报损失）− 模型、审核、运维与开发摊销成本。

上线前至少记录：任务量、真实采纳率、人工净节省时间、关键任务正确率、严重错误数、引用可追溯率、人工接管率、P95 任务完成时长、每个完成任务的模型成本、故障恢复时间。当前没有这些实测值，本文不对 ROI、准确率或容量做定量承诺。

## 6. 需要业务方作出的三项决定

1. **选择首个场景**：产品/制度问答与分流，或有权威实时数据可接的运营告警分析；明确业务 owner、人工兜底人与现有人工作业成本。
2. **批准风险门槛**：哪些问题必须转人工，哪些错误一票否决，试点用户与数据范围、RPO/RTO 和预算上限是什么。
3. **接受按证据立项**：长任务、自动续跑、模型队列、更多渠道/子代理等，只在相应损失达到业务约定阈值后开发。
