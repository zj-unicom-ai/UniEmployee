# UniEmployee 企业应用现状与迭代路线图

盘点基线：仓库 `main`，`v0.19.1`（2026-09-23）。本文根据当前源码、配置、测试目录与部署文档整理。它评估的是仓库具备的能力，不代表任何客户环境已经完成部署、压测或安全验收。

## 结论摘要

UniEmployee 已经从概念验证走到可交付的单企业试点平台：员工配置、知识检索、模型和工具编排、审批、Trace、用户管理、OIDC、PostgreSQL、沙箱和容器部署的主要链路都已存在。后端有 52 个测试模块，CI 执行后端 pytest 和前端构建；测试夹具把数据库固定为临时 SQLite。

适合的下一步是选一个部门、一个低风险流程，接真实且只读的数据，带人工复核上线。当前不建议按“多租户 SaaS、高并发、无人值守自动操作”直接对外承诺。以下差距会影响生产结果：

1. **演示数据进入默认启动路径。** `main.py` 启动时调用本体演示种子；其中含虚拟企业、网络运营演示数据和吉利/零跑模拟客户。CRM MCP 服务也是 mock 数据，退款工作流有硬编码订单。生产试点必须先让演示种子显式关闭或与生产租户/环境隔离。
2. **能力广，真实业务闭环尚未证明。** MCP、RAGFlow、Webhook 和数据源入口已具备，但仓库里的 CRM 示例不是企业系统的生产连接器；需要按目标场景接入真实系统，确认来源权限、数据时效、失败处理和写操作授权。
3. **当前部署形态是单应用实例。** Docker Compose 给出 PostgreSQL 和一个应用容器，应用使用进程内 Agent/MCP 缓存及定时调度器。调度任务有数据库 CAS 抢占，但 Agent 缓存无容量上限、无跨实例变更广播；多个应用副本的缓存/MCP 生命周期、长连接与任务执行语义仍需专项验证。
4. **可靠性与数据保护需补成运维机制。** 已有 `/livez`、`/readyz`、日志、Trace 和 PostgreSQL 备份脚本；数据库备份不包含 `workspace` 上传和报告文件。仓库未呈现备份恢复演练、保留期限、指标告警、灾备目标或外部对象存储策略。
5. **权限有基础，不等于全产品权限模型已完成。** 已有管理员/普通用户、员工分配、部门、OIDC 组映射及对话/审批/本体的部分租户过滤。`ENTERPRISE_TENANT_ID` 明确是单企业固定租户方案；数据分析数据源、资源目录和组织管理等需逐接口确认授权及租户边界，不能据此宣传完整多租户隔离。
6. **质量运营以人工反馈为主。** Trace、token 统计和用户反馈页面已实现；CI 没有 PostgreSQL 集成测试或基于黄金问题集的自动 Agent 回归评测。测试通过也不能单独证明回答质量、RAG 命中、真实连接器兼容或峰值容量。

因此，建议对外采用这个准确定位：**可以进入有业务负责人、只读数据、人工兜底的单企业试点；达到下文上线门槛后，再逐步扩展到正式生产和更多员工。**

## 当前能力盘点

| 领域 | 当前状态 | 企业应用判断 |
|---|---|---|
| 员工与资源配置 | 员工、技能、工具、知识库、SOP、连接器由 catalog 配置；已有 8 个示例员工 | 平台骨架完整。内置员工多为示范模板，需按企业岗位重做职责边界、知识和工具授权 |
| 对话运行 | FastAPI + LangGraph/deepagents；SSE；PostgreSQL checkpoint/store；摘要、断流保存、启动恢复 | 可支撑试点。模型超时、重试、回退、取消、成本预算及容量需按目标负载验证 |
| 知识与本体 | FAQ、Wiki、RAGFlow、多源检索、来源标注、本体实体关系和审计 | 接真实知识库前要确定负责人、版本/失效流程、权限过滤和引用验收 |
| 数据分析 | 独立分析工作台；SQL AST 只读校验、表白名单、行数上限和超时 | 安全设计较扎实；需使用目标生产库的只读账号、实际方言和数据量验证 |
| 人工审批 | 外层工具审批 + 退款 StateGraph 内层审批；审批记录持久化、过期处理 | 可用于少量高风险动作。需逐工具定义审批人、授权、幂等、重试和撤销/补偿 |
| 身份与访问 | JWT、本地密码、OIDC SSO、CSRF cookie、登录失败限流、角色/组织/员工分配 | 单企业身份接入有基础。登录限流是单进程内存；权限矩阵需做逐路由审查 |
| 执行与连接器 | MCP stdio/npx、Playwright、local shell、可选 OpenSandbox | 真实系统连接器仍要单独开发/配置；对生产开启 `local_shell` 应有严格工作目录、网络和凭据约束 |
| 自动化与渠道 | 定时/Webhook 自动化；平台内 Web/IM 频道框架 | 外部企业微信、飞书、钉钉渠道仍是后续工作；自动化先限于无副作用或经审批任务 |
| 数据存储 | 7 个 PostgreSQL 业务库；产物有个人工作区和显式部门共享 ACL；文件仍存在本地 `workspace` | 适合单节点试点。数据库脚本不会自动备份文件；容量、清理和联合恢复仍需设计 |
| 交付与质量 | Docker Compose；CI 跑 SQLite pytest 和前端构建；52 个测试模块 | 有开发质量基线；需补 PG 迁移/并发集成、浏览器关键流、评测集和发布回滚验证 |
| 可观测与运营 | request id、应用日志、Trace 输入输出/耗时/token、用户反馈、健康检查 | 有排障素材；需要运营仪表盘、告警、数据保留和敏感内容访问治理 |

## 建议的企业试点范围

先选一个每天发生、结果可核验、失败可由员工接管的流程。建议候选：

- **制度/产品知识问答与工单分流**：只读访问受控知识库；引用来源；不直接承诺或执行交易。最适合作为首个风险较低的试点。
- **运营告警影响分析**：只读接入告警、拓扑和工单数据；输出受影响对象、证据和建议，由值班人员确认。价值明显，但依赖真实遥测/拓扑和时效保障。

第一阶段不要同时上线多个岗位，也不要开放自动退款、改 CRM、批量通知或网络控制等写操作。试点章程需先定业务负责人、数据负责人、系统 owner、使用人群、人工兜底人、试点期限和退出办法。

## 分阶段迭代计划

### 阶段 0：上线阻断项与范围冻结（第 1–2 周）

- 增加明确的 `APP_ENV`/种子策略；生产模式默认拒绝播种任何虚构企业、客户、订单和运营数据；演示环境显式开启。
- 形成目标场景的数据流和权限清单：每个工具可读/写哪些系统、字段、租户和用户；先采用独立只读服务账号。
- 清理或显式隔离 mock CRM、硬编码退款订单以及演示数据生成入口；生产 UI/配置中标记演示资源，防止误绑定。
- 建立环境配置校验：生产启动拒绝弱 `JWT_SECRET`、默认 DB 密码、非 HTTPS 的安全 cookie、未授权执行后端和缺少必要备份配置；检查连接器密钥不进入 Trace/日志。
- 验收：新建生产环境启动后无任何虚构业务实体；试点用户只看到被分配员工；只读账号无法写目标业务库；每个试点问题都有责任人和预期答案/动作。

### 阶段 1：真实数据只读试点与质量门槛（第 3–6 周）

- 为选定的一个场景接入真实知识/业务源；明确身份透传或服务账号授权方式、同步间隔、数据 owner、来源和失效策略。
- 制作黄金用例（建议至少 50 条，含正常、边界、无答案、冲突、越权和过期数据），由业务 owner 标准答案并标注风险级别；建立离线重复运行和人工抽检流程。
- 展示答案引用、数据时间戳、工具调用结果和“不确定/转人工”入口；对高风险意图默认拒答或转人工。
- 在目标 PostgreSQL 版本和目标模型上做端到端验证；压测并记录并发、P95 首 token/总耗时、失败率、token 成本、RAG 引用准确度。
- 验收建议：黄金集关键问题正确率 ≥95%，引用可追溯率 100%，权限测试越权成功 0；高风险答案 100% 有人工处置路径。未达到时限定用户/问题范围，不以平均满意度掩盖高风险错误。

### 阶段 2：生产运维和受控写操作（第 7–10 周）

- **进行中：**产物工作区已支持个人归档和单文件部门共享，下载按租户/归属/部门 ACL 控制；共享文件不会连带开放来源会话。详见 [产物工作区指南](./artifact-workspace.md)。
- 把工作区文件纳入备份恢复、保留期限、权限和容量方案；完成数据库 + 文件联合恢复演练，记录 RPO/RTO。
- 配置 HTTPS、生产 SSO、密钥托管/轮换、数据库最小权限、日志脱敏；把登录限流改为共享存储或网关策略。
- 增加服务指标和告警：可用率、请求/模型错误、超时、工具成功率、队列/审批积压、模型成本、磁盘和 DB 容量；建立值班手册和故障演练。
- 建立 PostgreSQL CI 集成矩阵，覆盖 schema migration、并发、关键筛选和 LangGraph checkpoint/store；发布时执行备份、版本迁移、健康检查和可回滚步骤。
- 对确有业务收益的写操作逐个启用：先幂等键、最小权限、参数校验、审批人/超时、执行后核验、失败补偿和审计，禁止“模型可任意写”。
- 验收：恢复演练满足业务书面批准的 RPO/RTO；审批全链路可重放且重复提交不重复产生业务副作用；告警演练能通知到值班责任人。

### 阶段 3：扩面与多实例（第 11–16 周及之后）

- 基于试点数据决定是否扩展第二员工/部门；每个员工单独做知识、权限、评测和负责人验收。
- 若需要高可用/水平扩容，先将 Agent 配置/缓存失效、MCP connector 生命周期、SSE 连接、定时任务执行、附件与报告存储做成跨实例一致的设计，再部署多应用副本。
- 增加 Agent 配置和技能版本历史、审批式发布、灰度、回滚；按部门/员工做配额和成本限额。
- 只有当多个独立客户确实共用同一服务时，才启动完整多租户专项：catalog/组织/资源/文件/trace/数据源/connector 全表 tenant 过滤与隔离测试；否则使用独立部署边界，避免过早引入 SaaS 复杂度。
- 根据用户日常工作渠道需求，接入一个企业 IM 渠道并做身份映射、消息幂等、附件、限流、重试和失败回执。

## 上线前 Go/No-Go 清单

- [ ] 生产启动不写入演示实体/模拟客户/模拟订单；真实连接器已经替换 mock。
- [ ] SSO、HTTPS、强密钥、最小权限、用户/部门/员工授权和越权用例通过。
- [ ] 高风险工具默认关停或有可验证的审批、幂等、审计与人工兜底。
- [ ] 目标模型、数据库、知识源和连接器完成端到端及故障测试；黄金集达到业务批准阈值。
- [ ] 数据库与 workspace 文件都纳入备份；恢复演练成功，RPO/RTO 有业务签字。
- [ ] 监控、告警、值班人、故障升级和供应商不可用时的降级/人工接管流程已明确。
- [ ] 试点用户、员工范围、并发上限、成本预算、数据保留/删除期限和退出流程已书面确认。

## 建议的项目指标

上线前由业务 owner 定目标值；至少按周观察：任务完成率、人工接管率、引用正确率、越权拦截数、工具成功率、P95 完成时间、单任务模型成本、审批耗时、节省的人工作业时间、用户采纳率。高风险错误和越权应独立计数，不应并入平均质量分。
