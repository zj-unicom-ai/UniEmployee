> 状态：首版文本消息链路已打通；生产化验收未完成，尚未放行生产集成

## 1. 结论与实施边界

首版只支持文本消息、单聊和群聊 `@` 机器人；不申请“读取群内全部消息”的高敏权限，不做图片/文件、消息卡片交互、撤回、编辑或流式逐字更新。机器人回复优先调用“回复消息”接口关联原消息；自动任务等主动通知调用“发送消息”接口。

飞书事件采用“至少一次”投递，接收方必须快速确认且可能收到重复事件。UniEmployee 当前 `/api/im/channels/{id}/incoming` 会同步等待 AI 完整回复，不能直接作为飞书回调。接入必须拆成：

```text
飞书事件 → Transport 验证/解密 → 标准化 → Inbox 去重并落库 → 立即确认
                                              ↓
                                     Worker 调用数字员工
                                              ↓
                              Outbox 持久化 → 飞书 API → 状态回写
```

已确认生产环境没有公网 HTTPS 域名，因此首版采用官方 SDK 长连接：UniEmployee 主动连接飞书，不需要暴露公网回调地址。Transport 仍保留协议边界，未来若切换 HTTP Webhook，只替换事件接入层，后续标准化、Inbox、Worker 和 Outbox 不变。部署环境必须能够主动访问飞书开放平台的 HTTPS 与 WebSocket 地址。

## 2. 已核验的飞书协议事实

- 消息事件为 `im.message.receive_v1`，事件 2.0 包含 `header.event_id`，消息体包含 `message_id`、`chat_id`、`chat_type`、`message_type`、`content`、`mentions` 等字段。[接收消息](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive)
- 事件处理需要在约 3 秒内成功确认；失败会重试，即使成功也可能重复投递。因此 AI 推理绝不能位于回调响应路径，必须持久化去重。[事件概述](https://open.feishu.cn/document/server-docs/event-subscription-guide/overview)
- 自建应用使用 App ID、App Secret 获取 `tenant_access_token`，以应用身份调用消息 API；凭证需要缓存并在失效后刷新。[获取自建应用 tenant_access_token](https://open.feishu.cn/document/server-docs/authentication-management/access-token/tenant_access_token_internal)
- 发送接口使用 `receive_id_type` 与 `receive_id`；消息 `content` 是 JSON 序列化后的字符串。[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)；[消息内容结构](https://open.feishu.cn/document/server-docs/im-v1/message-content-description/create_json)
- 对收到的消息可调用回复接口；首版保留源 `message_id`，避免把回答误发到其他群或私聊。[回复消息](https://open.feishu.cn/document/server-docs/im-v1/message/reply)
- 官方已将新项目的会话机器人能力迁移到独立的 Channel SDK；当前 PoC 候选为 `lark-channel-sdk==1.4.0`，版本行为必须通过真实收发后再写入生产依赖锁。[官方 Channel SDK](https://github.com/larksuite/channel-sdk-python)

所有控制台权限名称与 SDK 版本均在测试企业的开放平台控制台二次确认，禁止凭记忆写死。保存官方事件日志中的脱敏样例作为契约测试 fixture。

## 3. 目标架构与代码边界

新增 `backend/app/im/`，避免与 MCP `connectors/` 混淆：

```text
im/contracts.py              # NormalizedInbound、OutboundMessage、DeliveryResult
im/context.py                # ActorContext：会话主体与授权主体分离
im/identity.py               # 外部身份解析；为后续平台账号绑定预留
im/service.py                # 去重、路由、会话解析、任务编排
im/jobs.py                   # Inbox/Outbox 建表、CAS 抢占、重试状态机
im/worker.py                 # 后台消费与优雅停机
im/transports/base.py        # 事件接入 Transport 协议
im/transports/feishu_ws.py   # 官方 SDK 长连接及生命周期
im/providers/base.py         # 消息 Provider 协议
im/providers/feishu.py       # 飞书事件解析、Token、回复/发送 API
```

同时将 `_stream_run()` 的核心执行抽成返回内部类型事件的 async iterator；SSE 路由和 IM Worker 分别做适配。禁止继续在 IM 代码里解析 `data: ...` 字符串，否则前端协议变化会破坏机器人。

### 数据模型

沿用 `conversations` 数据库，新增：

- `channel_credentials`：`channel_id`、`app_id`、加密后的 App Secret、`tenant_key`、更新时间；Verification Token / Encrypt Key 仅作为未来 Webhook Transport 的可空字段，不是首版长连接必填项。独立 `IM_CREDENTIAL_KEY` 加密；启用飞书时未配置该密钥应拒绝启动，不回退到 JWT 密钥。
- `channel_inbox`：内部 ID、`channel_id`、`provider_event_id`、`provider_message_id`、载荷摘要/必要字段、状态、尝试次数、租约、错误和时间戳。对 `(channel_id, provider_message_id)` 建唯一约束，`event_id` 作为审计字段；实际事件样例确认重投行为后再冻结最终幂等键。
- `channel_outbox`：Inbox ID、目标、源消息 ID、内容、稳定 UUID、状态、尝试次数、下次重试时间、飞书消息 ID和错误。
- `channel_identities`：按 `(app_id, tenant_key, open_id)` 标识飞书用户，预留可空的 `internal_user_id`、绑定状态和审计时间；首版保持为空，严禁用显示名作为身份键。
- `channel_threads`：`channel_id`、`tenant_key`、`chat_id`、`sender_open_id`、`root_id`、`employee_id`、`conv_id`。解决现有模型把同一发送人在不同群里的消息串到同一会话的问题。

首版会话策略已经确定：单聊按 `tenant_key + chat_id`；群聊按 `tenant_key + chat_id` 全群共享记忆。同一群成员可以看到并延续彼此触发的机器人上下文，因此不得在共享群会话中注入个人私有数据。事件仍保存 `sender_open_id`、`root_id/parent_id`，为审计及后续话题模式预留，但首版不据此拆分会话。每个飞书频道必须且只能有一个默认数字员工，多员工路由另立需求。

## 4. 分阶段实施与验收门

### 步骤 0：冻结外部条件和协议

1. 创建测试企业的企业自建应用，启用机器人能力；禁止误用只能做群通知的“自定义机器人”。
2. 确认场景为“单聊 + 群聊仅被 @ 时响应”，核对最小权限并订阅 `im.message.receive_v1`。
3. 使用官方 SDK 长连接接收事件，验证生产网络可以访问飞书 HTTPS/WebSocket，验证断线自动重连和进程优雅停机。
4. 用飞书 API 调试台和一个独立 PoC 完成 Token 获取、发送文本、长连接接收事件、回复原消息。
5. 固定已验证的 SDK 版本，保存脱敏的单聊、群聊 @、非文本和重复事件样例。

仓库提供 `scripts/verify_feishu_connection.py` 作为隔离 PoC。凭证仅通过 `FEISHU_APP_ID`、`FEISHU_APP_SECRET` 环境变量注入；先以 `--security-mode audit --reply` 验证，再以 `--security-mode strict --reply` 重跑。脚本不访问业务数据库，也不记录消息正文或密钥。

**验收门 G0：** 测试应用已发布到限定可用范围；PoC 能完成一次单聊和一次群聊 @ 的收发；长连接事件处理函数在 500 ms 内完成落库并返回；主动断网后能自动恢复；权限清单、SDK 版本、事件样例进入文档。G0 未通过，不修改业务数据模型。

截至 2026-09-20：凭证校验、长连接单聊入站和回复 API 已通过真实租户测试；官方最小 Echo 示例和 UniEmployee 完整业务链路均已成功收发。群聊 `@`、strict 模式、断网重连尚未验收，因此 G0 仍为部分完成。开发机在 VPN/代理路径下仍可能收到不符合 Python/OpenSSL 安全级别的证书；测试始终没有关闭 TLS 校验。生产放行前必须在实际部署网络复验全部 HTTPS/WSS 节点，飞书连接默认走直连，代理使用必须显式配置。

### 步骤 1：建立内部契约和持久队列

1. 定义与飞书无关的标准消息、目标和投递结果类型。
2. 为上述五类表编写双方言 DDL、幂等迁移和 CAS 抢占逻辑。
3. 明确状态机：`received → processing → completed/failed`，Outbox 为 `pending → sending → sent/retry/dead`；租约超时可回收。
4. 写入事件仅保留处理必需字段；原始正文按现有审计政策决定是否保留，不默认永久保存。
5. 在内部执行上下文中拆分 `subject_id`（稳定的会话/记忆主体）和 `authorization_user_id`（可空的平台授权主体）。首版飞书消息只有前者，后续绑定只需填充后者。

**验收门 G1：** SQLite 与 PostgreSQL 均通过迁移测试；并发插入同一消息仅生成一条 Inbox；Worker 崩溃后租约任务可被重新领取；密钥不出现在列表 API、日志或异常中。

截至 2026-09-14：G1 隔离实现已接入应用启动生命周期；SQLite 10 项测试、PostgreSQL 实库迁移/幂等/CAS 领取测试均通过。PostgreSQL 宿主机映射端口为 15432，容器内部仍为 5432。凭证密文、Inbox/Outbox、外部身份和群聊共享会话表已建立。G1 不启动飞书连接，连接仍由后续 Provider 阶段控制。

### 步骤 2：重构数字员工执行内核

1. 从 `streaming.py` 提取协议无关的 `run_agent_events()`。
2. SSE 层继续输出原有事件格式，确保 Web 聊天无行为变化。
3. 增加文本结果收集器供 IM 与自动任务调用，统一错误、审批中断和 Trace 处理。
4. `run_agent_events()` 接收结构化 `ActorContext`，禁止继续用一个 `user_id` 同时代表会话归属、长期记忆和权限身份；这是后续安全绑定无需重写执行链路的前置条件。

**验收门 G2：** 现有 pytest 全部通过；新增测试证明同一输入经 SSE 与文本收集器得到相同最终回答、Trace 状态一致；人工回归 Web 聊天流式输出、工具调用和审批。

### 步骤 3：实现飞书 Provider

1. 使用官方 SDK 建立长连接并复用其连接鉴权、事件分发能力；业务层仍校验事件 `app_id` 和已绑定 `tenant_key`，拒绝跨应用或跨租户数据。
2. 只接收 `im.message.receive_v1`；过滤机器人、自身消息、非文本消息和不符合群聊 @ 策略的消息。
3. 解析 `content` 的内层 JSON，并依据 `mentions` 精确移除机器人占位符，不能用字符串猜测机器人名称。
4. 实现 Token 缓存、主动刷新、一次 401 后强制刷新重试；API 域名固定，不接受数据库中的任意 URL，避免 SSRF。
5. 实现“回复原消息”和“向 chat_id 主动发送”两条出口，Outbox UUID 在重试间保持不变。
6. 增加长连接 Supervisor：随应用生命周期启动/停止，记录连接状态和重连次数；多实例只依赖飞书的集群投递与数据库幂等，不依赖进程内锁。

**验收门 G3：** 所有 G0 fixture 通过契约测试；错误凭证无法建立连接，错误 App ID、错误租户、畸形载荷均被拒绝且不入队；重复事件只入队一次；模拟 401、429、5xx、超时可得到预期的刷新、退避或 dead 状态。

### 步骤 4：接通 Worker 与会话映射

1. 长连接事件处理函数只完成校验、标准化和 Inbox 落库，然后立即返回成功。
2. Worker 使用数据库 CAS 领取任务，按会话策略解析或创建 `conv_id`，调用默认数字员工。
3. 最终回答先写 Outbox，再发送飞书；进程重启后可继续未完成投递。
4. 当数字员工触发 HITL 审批时，首版发送明确的“请前往平台处理”文本和平台链接，不在飞书中直接审批。

**验收门 G4：** 注入 30 秒 AI 延迟时事件处理函数仍低于 500 ms；两个群不串上下文，同一群内两个用户能延续共享上下文；10 个重复事件只产生一次模型执行和一次逻辑回复；在“入队后/模型后/发送前”强杀进程，重启均可恢复且不丢消息。

### 步骤 5：管理界面与配置安全

1. 将 `ImView.vue` 从占位页改为频道列表、飞书配置表单、员工绑定、启停、连接测试和最近事件状态。
2. App Secret 等字段仅允许写入/替换，读取时只返回 `configured: true` 和掩码；前端永不回填明文。
3. “验证配置”分成凭证验证与收发测试，不能仅以保存成功代表已接通。
4. 展示 Transport、长连接在线状态、最近重连/入站/出站时间和最后错误；首版不展示不存在的回调 URL、Verification Token 或 Encrypt Key。启用前要求所有必填检查通过。

**验收门 G5：** 浏览器完成新增、修改非密钥字段、替换密钥、禁用和重新启用；网络响应及服务日志中无明文密钥；无管理员权限返回 403；配置错误能定位到凭证、权限、长连接或发送阶段。

### 步骤 6：端到端验收与灰度

在测试企业执行以下矩阵：单聊、群聊 @、群聊未 @、重复推送、长文本、特殊字符、模型超时、服务重启、飞书限流、Token 失效、机器人被移出群、应用权限撤回。验证会话隔离、Trace、敏感词护栏和审计日志。

先仅对测试用户开放，再对一个试点群开放。保留 `FEISHU_ENABLED=0` 总开关和频道级禁用；回滚只停止新事件消费，Inbox/Outbox 数据保留以便审计和恢复。

**验收门 G6：** 连续 24 小时灰度无重复回复、无串会话、无密钥泄露；所有失败均可从 `request_id → inbox_id → conv_id → outbox_id → feishu_message_id` 追踪；运维人员完成禁用、重试 dead job 和密钥轮换演练后方可扩大范围。

### 步骤 7（后续版本）：安全绑定 UniEmployee 平台账号

本步骤不阻塞首版上线，但首版的数据模型和 `ActorContext` 必须提前兼容，不得等绑定需求出现后再拆身份概念。

1. 已登录 UniEmployee 的用户在个人设置中申请一次性绑定码；只保存绑定码哈希，设置短有效期、最大尝试次数和单次消费约束。
2. 用户只能在机器人单聊中发送 `/bind <code>` 完成绑定；群聊中的绑定指令一律拒绝，防止验证码暴露和主体混淆。
3. 服务端同时验证平台登录主体、绑定码、`app_id + tenant_key + open_id` 和账号状态，成功后写入 `channel_identities.internal_user_id`，并记录审计事件。
4. 每次单聊执行都实时读取平台账号状态和授权，不把角色或权限复制到绑定表；平台账号禁用、权限调整或解绑应立即生效。
5. 绑定仅影响后续授权，不自动合并或迁移既有外部身份的历史会话与长期记忆。是否迁移必须另做显式、可审计的数据迁移功能。
6. 提供用户自助查看/解绑、管理员只读审计和异常解绑能力；绑定码、完整 open_id 和敏感凭证均不得写日志。
7. 群聊仍固定使用频道级最低权限。绑定用户在群里发消息时，`internal_user_id` 只用于审计，不用于提升群会话权限；需要个人数据或个人权限时，引导至单聊或 Web 平台。

**验收门 G7：** 覆盖绑定成功、过期、重复使用、错误用户、群聊绑定拒绝、账号禁用、权限实时变化和解绑；证明不能按姓名/邮箱误绑定，不能通过绑定提升群聊权限，不能自动访问或合并旧历史；完整链路有审计且不泄露绑定码。通过独立安全评审后才能启用 `FEISHU_ACCOUNT_BINDING_ENABLED=1`。

## 5. 测试、可观测性与完成标准

## 7. 飞书身份绑定的含义与首版建议

“绑定平台账号”是把飞书事件中的稳定身份 `(app_id, tenant_key, open_id)` 映射到 UniEmployee 的 `users.id`。绑定后系统才可以确认“这个飞书用户就是平台里的某个账号”，并在每次请求时按该平台账号实时检查员工分配、角色、私有知识库和数据源权限。

“隔离的外部身份”则是不做这层映射。身份唯一性仍由 `(provider, app_id, tenant_key, open_id)` 保证；会话/记忆主体使用由应用、飞书外部租户和会话计算出的 `im_feishu_<sha256>` 安全标识，避免外部标识泄露到目录名并兼容 Windows 文件系统。它不能进入该用户的 Web 历史会话，也不能因为姓名、邮箱相同就获得平台角色、个人数据源或管理员权限；只能使用飞书频道明确授权的默认员工和频道级能力。这样可以避免同名误绑定、伪造身份和权限提升。

首版已经确定不绑定，适用于公共知识问答、低风险工具以及“审批回平台处理”的场景。凡是需要查询个人数据、访问私有数据源、继承员工分配、以本人身份执行业务动作或合并 Web/飞书历史的需求，都必须先实施步骤 7。绑定由已登录的平台用户生成高熵、短时、一次性绑定码，在机器人单聊侧确认后落库，并支持审计、解绑和禁用；禁止按显示名、手机号或邮箱自动匹配。

由于已选择“群聊记忆全群共享”，群会话必须始终按频道级最低权限执行。即使未来某位群成员绑定了管理员账号，也不能把其个人权限或私有结果写入全群共享上下文；需要个人权限的操作应转到单聊或 Web 平台完成。
